# 107. 設計書 — FB品質ルールの来歴トレーサビリティ

- 作成日: 2026-08-14
- 発端: docs/106 §2（運用者提案「文書にあるのに実装されていない時点で落とせないか」）
- 関連: docs/42（FB品質SSOT）/ docs/97 柱4（全ての指示行に来歴を付ける）/ docs/93 §0・docs/106 §1A（「書いただけ」事故の実例）

## 0. 何を解決するか

docs/42 にルールを書いても、プロンプト・テスト・検査のどこにも落とさなければ実装されない。
この「書いただけ」事故は既に2度起きた（生の数値ルール・動画取り違え）。
**完全な意味判定は不可能**（散文ルールが台本に意味的に実装されているかを機械は判定できない）が、
**「どこに実装したかを一度も宣言していない」ことは機械的に落とせる。** 本設計はそれだけを狙う。

## 1. 仕組み

### 1.1 ルールID
docs/42 の規範的なルール（〜する／〜しない、と実装先に要求する行）に ID を振る。

- 形式: `[FB-042-<節>-<連番>]`。節はゼロ埋め2桁、小節はドット付き（例: `[FB-042-06-3]` = §6 の3番目、`[FB-042-02.1-2]` = §2.1 の2番目）
- ID は行末に付ける。説明・背景・表・経緯の行には付けない（規範だけ）
- ルールを削除したら ID も消す。改番はしない（欠番を許す。連番の意味は「振った順」だけ）

### 1.2 実装側の宣言（3つのどれかがあればよい）
| 形 | 書き方 | 例 |
| --- | --- | --- |
| プロンプト/コードで実装 | 実装箇所の近くのコメントに ID | `llm.py` の SYSTEM_PROMPT 直上のコメントブロック、`scrub_markdown()` のコメント |
| テストで担保 | テストの docstring に ID | `test_scrub_markdown.py` の docstring |
| soar_eval の検査 | `checkers.py` の `RULES[...]` に ID | `"N5": [..., "FB-042-06-3"]` |

skill版（`.claude/skills/vocal-trainer/SKILL.md`）は Markdown コメント `<!-- [FB-042-…] -->` で該当節に付ける。

### 1.3 テストによる強制（`backend/tests/test_fb_rule_traceability.py`）
1. **順方向（事故検出の本体）**: docs/42 から ID 集合を抽出し、実装側スキャン対象
   （`llm.py`・`persona.py`・`rule_engine.py`・`tools.py`・SKILL.md・`backend/tests/**`・`checkers.py`）
   の ID 集合がそれを**包含**することを検証。宣言の無い ID があれば落ちる
   ＝「書いたが一度も実装しなかった」を機械的に検出
2. **逆方向**: 実装側にあって docs/42 に無い ID は落とす（typo・docs/42 から消したのに実装側に残った宣言＝SSOT逸脱）

## 2. 限界（正直に）

- ID の宣言は「担当者がどこに実装したかを一度は考えて書いた」ことしか保証しない。
  **実装の意味的な正しさ・十分さは保証しない**（それは soar_eval・レビュー・ブラインド判定の仕事）
- 宣言だけして実装しない不正は可能。ただし宣言はコメントとして実装箇所の隣に残るため、
  レビューで嘘が見える形にはなる

## 3. 運用ルール（docs/42 冒頭にも同旨を追記）

- docs/42 に規範ルールを足す時は **ID を振り、同じPRで実装側の宣言を書く**（テストが強制する）
- 機械で測れるルールは宣言だけで済ませず、soar_eval のチェッカに落として数で追う
  （既存: N4 冗長・N5 生の数値・H1〜H8 捏造系。docs/106 §2 の候補リスト参照）

## 1. システム構成

```
[登録フォーム/設定画面] ─ opt_in ─> users.newsletter_opt_in
[運用者CLI] send_newsletter.py ──> mail_service.send_mail() ──> Brevo ──> 会員
     │            │
     │            └─ 送信成功を newsletter_sends に記録（冪等性の台帳）
     └─ 対象抽出: opt_in=true ∧ 実会員 ∧ campaign未送信
[メール内 配信停止リンク] ──> GET /api/v1/mail/unsubscribe?token= ──> opt_in=false
```

## 2. アーキテクチャ判断
- **配信はバッチ（手動CLI）**: リリース告知は都度イベントで cron 不要。`send_practice_reminders.py` と同じ「backend importable スクリプト＋DRY_RUN」方式（運用の学習コストゼロ）。
- **冪等性は台帳テーブルで**: `newsletter_sends(user_id, campaign_key)` UNIQUE。再実行＝未送信者だけに送る。送信上限250/実行（FR-05）も「打ち切り→再実行で続き」が台帳で自然に成立する。
- **配信停止はbackend直（フロント画面なし）**: GET が簡易HTMLを返す。トークンは `secrets.token_urlsafe(32)`（43字・推測不能）。POSTでなくGETなのはメーラーのワンクリック動作要件のため（副作用は opt_in=false のみ・冪等）。
- **計測パラメータの命名統一**: メールリンクは `src=mail_*`（welcome=`mail_welcome`、告知=`mail_news_<campaign_key>`）に統一し、日次レポートの突合を `src=mail` 前方一致へ広げる。→ 告知メールのクリックも自動で「📩 メール経由」に乗る。既送のwelcome 2通（旧 `src=welcome_mail`・運用者のテスト）だけ集計対象外になるが実害なし。
- 検討した代替案: Brevoキャンペーン機能（管理画面配信）→ 開封計測が付くが、文面管理がコード外に出て docs 正本の規律が崩れる＋API/画面の学習コスト。会員数百人までは自前バッチが軽い。

## 3. API設計

| メソッド/パス | 認証 | 内容 |
| --- | --- | --- |
| `POST /api/v1/auth/register` | 不要 | body に `newsletter_opt_in: bool = false` 追加。true なら token も生成 |
| `GET /api/v1/auth/me` | 要 | レスポンスに `newsletter_opt_in` を追加 |
| `POST /api/v1/auth/newsletter` | 要 | `{"opt_in": bool}` → 自分の opt_in を更新。ONにした時 token 未発行なら生成。200 `{"opt_in": <新値>}` |
| `GET /api/v1/mail/unsubscribe?token=` | 不要 | 有効: opt_in=false にして「配信停止しました」HTML(200)。無効/欠落: 「このリンクは無効です」HTML(200)。500を出さない |

## 4. DBスキーマ（マイグレーション: down_revision=`d1e2f3a4b5c6`＝login_events）

## 7. エラーハンドリング方針
- バッチ: 1通の失敗はログして続行（他の会員へ影響させない）。台帳は**成功時のみ**記録＝失敗者は再実行で再送。
- unsubscribe: トークン不一致・欠落は200のHTMLで完結（存在推測を許す404/500を出さない）。
- register の opt_in 保存はユーザー作成と同一トランザクション。

## 8. 性能・可用性
- 250通 × 直列送信（10s timeout）でも最悪42分 → 実運用は数十人規模で数十秒。並列化は不要（Brevoレート制限回避を優先）。

## 9. セキュリティ
- token は暗号学的乱数・URLに個人情報なし・ログに出さない。
- POST /newsletter は本人のみ（get_current_user）。他人の opt_in は変更不可。

## 10. テスト方針
- 単体: token生成・unsubscribe（有効/無効/再実行）・send_mail共通化の回帰。
- 結合: register(opt_in有無) / me / POST newsletter / バッチ対象抽出と冪等性（sqlite）。
- 既存90テストの回帰なし。

## 11. 移行 / 後方互換性
- 既存会員: opt_in=false 初期化（送信対象外）。既存挙動の変化はゼロ。
- 起動時 `alembic upgrade head` で自動適用（本番SQLite・現行デプロイのまま）。
- ロールバック: revert のみ（列は残っても無害）。

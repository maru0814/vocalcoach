# 生徒カルテと主観問診 機能要件書

関連: docs/42（FB品質正本・不変）, docs/43/52（zero-base FB）, docs/31（有料プラン）。背景: Fable設計レビュー「リアルのボイストレーナーに近づける」提案の優先1・2（カルテ＝セッション横断の記憶、問診＝感覚の活用）。CEO優先順位: 継続率（サブスク維持）に直結するため、実演音源・レッスン構造より先行。

## 1. 概要
- **一言**: ソラ先生が「生徒を覚えている」ようにする。ユーザー単位の生徒カルテ（声の特徴・持ち癖・練習履歴・宿題・本人の感覚）を永続化し、レッスン冒頭の引き継ぎと、音響解析×本人の感覚の突き合わせ診断を可能にする。
- **解決する課題**: (1) 現状はセッションが変わると生徒を忘れる（`ChatSession` 単位の状態のみ。ユーザー単位の記憶が無い）。本物のトレーナーは「先週の宿題どうだった？」から始める。(2) 診断が音響解析のみで、本人の感覚（楽/苦しい・力み）を使っていない。実際のレッスンは両方を突き合わせる。

## 2. 想定ユーザー / ユースケース
- **継続ユーザー（無料・有料とも）**: 週1回以上練習し、複数セッションを跨いで使う。前回の続きから自然に再開したい。
- **UC-1**: 2回目以降のセッション開始時、ソラ先生が「前回は『息漏れを減らす』のストロー発声を宿題にしましたね。やってみてどうでした？」と切り出す。
- **UC-2**: 録音FBの後にソラ先生が「今の高音、喉はラクでしたか？」と1問だけ聞く。「ちょっと苦しかった」と答えると、以降のFBが「解析では地声で押し上げ気味＋ご本人も苦しさを感じている→ミックスに寄せる練習を優先」のように両方を根拠にする。

## 3. スコープ
### 3.1 対象（やること）
- ユーザー単位の生徒カルテの永続化と自動更新（DB。手動編集なし）。
- カルテのプロンプト注入（チャット文脈・zero-base の evidence 両方）。
- セッション開始時の引き継ぎ挨拶（前回の課題・宿題への言及）。
- 録音FB後の主観問診（条件付き・1問だけ）と、回答のカルテ記録・診断への反映。
- 問診回答のレッドフラグ検知（痛み・嗄声）→ 既存の安全方針（受診案内）への接続。

### 3.2 対象外（やらないこと）
- カルテの閲覧・編集UI（frontend画面）。MVPはサーバー内のみ。表示は将来 designer 案件。
- カルテのLLM要約（MVPはルールベース集計のみ。コスト増なし）。
- 実演音源・レッスン構造（ウォームアップ/まとめ）＝「その後」フェーズ。
- Claude Code skill 版への展開（Webのみ。skillはステートレスなため対象外）。

## 4. ユーザーストーリー
- US-01: 生徒として、前回の続きから始めてほしい。毎回ゼロから説明したくない。
- US-02: 生徒として、感じたこと（苦しい・出しやすい）を伝えたら、それを踏まえて教えてほしい。
- US-03: 生徒として、喉の痛みを伝えたら、無理をさせず正しい対処（休声・受診の目安）を教えてほしい。
- US-04: 運営者として、カルテはアカウント削除と一緒に消えてほしい（個人データの後始末）。

## 5. 機能要件
### FR-01: 生徒カルテの永続化と自動更新
- **概要**: ユーザー1人につきカルテ1件（user_id 一意）。以下をシステムが自動更新する。
- **保持項目**:
  - 声の特徴: 声域（実測f0範囲の集約）、声タイプ（voice_type診断があれば）、よく歌うジャンル/曲（song_titleの履歴上位）。
  - 持ち癖: 診断課題の頻度上位3件（task_id＋回数。例: breathy_closure×4）。
  - 練習履歴: 勧めた基礎練と結果（達成/未達/切替）。直近10件。
  - 宿題: 最後のセッションで最後に勧めた基礎練（task_id＋practice名）と出した日。
  - 主観メモ: FR-03の問診回答（直近5件。日付＋要旨）。
  - 前回サマリ: 最終セッションの課題・到達点（1〜2行。ルールベース生成）。
- **更新タイミング**: 録音FB確定時（課題診断・達成判定後）と問診回答時に同期更新。バッチ不要。
- **例外**: カルテ更新失敗はFB本体を止めない（ログのみ）。

### FR-02: カルテのプロンプト注入
- **概要**: `build_session_context`（チャット・zero-base evidence の共通土台）に「この生徒について（カルテ）」ブロックを追加する。
- **詳細仕様**: 注入は要約形式で **500字以内**（プロンプト肥大防止）。事実忠実性ルール（docs/42）に従い、カルテに無いことは語らない。持ち癖は「過去の傾向」であり今回の録音の断定材料にしない（今回の実測を優先）。
- **例外**: カルテ未作成（初回ユーザー）は注入なし＝現行動作。

### FR-03: 主観の問診（1問だけ）
- **概要**: 録音FBの末尾に、条件を満たす時だけ感覚を1問聞く。
- **発火条件**（いずれか。ただし**同一セッションで最大2回**・連続ターンでは聞かない）:
  - そのセッションで最初の録音FBの後。
  - 力み系の課題（throat_tension）または高音での押し上げ（pulled_chest相当）を検知した後（「高いところ、喉はラクでしたか？」）。
  - 基礎練の達成判定の後（「やってみて、どこか力む感じはありましたか？」）。
- **回答の扱い**: 次のテキストメッセージを問診回答として扱い（明示的な構造化入力は求めない）、要旨をカルテの主観メモに記録。以降のFB・チャット文脈に「本人の感覚」として注入する。
- **例外**: ユーザーが答えず別の話題を振ったら深追いしない（1回で流す）。

### FR-04: 感覚×実測の突き合わせ
- **概要**: 主観メモがある時、FBは「実測」と「本人の感覚」の両方を根拠にする。
- **詳細仕様**: プロンプトに指針を追加:「本人の感覚は実測と同格の証拠。矛盾する時は否定せず両立させる（既存の声区ルールと同じ作法）。感覚が『苦しい・痛い』系なら練習強度を上げない」。
- **例外**: 感覚だけを根拠に数値・秒数を作らない（捏造防止は既存ガードのまま）。

### FR-05: レッドフラグ→安全接続
- **概要**: 問診回答に痛み・嗄声・声が出ない等のレッドフラグ語が含まれたら、練習継続を勧めず、休声と受診目安（2週間以上続く嗄声等）を案内する。
- **詳細仕様**: 検知語リストはルールベース（痛い/ヒリヒリ/枯れ/かすれ/血/出なくなった 等）。該当時はカルテに safety フラグを記録し、当該セッションでは高負荷練習（ベルティング等）を提案しない。
- **例外**: 医療診断はしない（既存方針どおり。voice-health の線引きに従う）。

### FR-06: セッション開始時の引き継ぎ（2026-08-06 改定・実ユーザーFB起点）
- **概要**: 新セッション作成時の初回コーチメッセージは、前回からの継続感を短く伝える。**宿題・練習名には言及しない**。
- **詳細仕様**:
  - 開始挨拶のモードは3つだけ: 同日再訪＝短い出迎えのみ（要約も読み上げない）／翌日以降＝前回サマリに軽く触れる／30日以上＝「久しぶりですね」系。
  - 宿題はカルテに保持し、**FB・練習提案の文脈でだけ**参照する（例:「前回の宿題『◯◯』と同じ内容ですが」「以前出した『◯◯』をもう一度やってみましょう」）。LLMへのカルテ注入時にこの作法を指針として添える。
  - 改定理由: 新しいテーマで始まるかもしれない場の開始挨拶で前回の宿題を蒸し返すのは不自然（2026-08-06 実ユーザーFB）。さらに旧仕様では、会話に登場していない練習名を挨拶が「さっき『◯◯』のお話をしましたね」と引用する捏造が起きた（同日報告）。
- **捏造防止（宿題データの真実性）**: 宿題としてカルテに記録してよいのは、コーチが会話で**実際に提示した**（表示テキストに練習名が登場した）基礎練だけ。ゼロベースFB（docs/52）は初回に練習を出さない（docs/42 §8 段階的エンゲージメント）ため、診断確定時に無条件でカタログ代表練習名を記録すると、FBでの宿題参照も捏造になる。対策は三層:
  1. 録音FB時: 表示した講評に練習名（または練習名に含まれる既知語彙）が無ければ宿題に記録しない
  2. チャット/チップで実際に練習を提示したターンで宿題を記録する（提示が診断より後に来るゼロベースFBの主経路）
  3. セッション開始時: 宿題の練習名が「ユーザー発言より後のコーチ発言」に一度も登場していなければ宿題を破棄する（既存の汚染データの自己修復。旧仕様の開始挨拶自身の言及は照合対象に含めない）
  - 併記: 前回サマリ（continueモード挨拶）に内部課題ID（例: breathy_closure）を露出させず、taxonomy のラベルに翻訳して記録する。

## 6. 非機能要件
- **プライバシー**: カルテは個人データ。アカウント削除時に連鎖削除（cascade）。エクスポートはスコープ外。
- **性能**: カルテ読み書きは録音FBフローに同期で乗るため、1クエリ＋1アップサートに収める。
- **コスト**: MVPは追加LLM呼び出しゼロ（集計・要約はルールベース）。プロンプト増は500字以内。
- **保守性**: カルテ項目はJSONカラムで開始（スキーマ進化を許容）。docs/42 のFB方針は不変。

## 7. 受け入れ基準
- AC-01（2026-08-06 改定）: ユーザーAがセッション1で課題「息漏れ」＋基礎練を受けて終了→セッション2を開始すると、初回メッセージは継続感のある挨拶になるが、**宿題・練習名には言及しない**。宿題への言及はFB・練習提案の文脈でのみ現れる。
- AC-02: セッション2の録音FB・チャットで、カルテの持ち癖（例: 息漏れ傾向）が文脈として参照できる（プロンプトに注入されている）。
- AC-03: 初回ユーザー（カルテ無し）は現行と同一の挙動（注入・引き継ぎなし）。
- AC-04: 最初の録音FBの後に感覚の質問が1問付く。直後のユーザー回答がカルテの主観メモに記録され、次のFBの文脈に「本人の感覚」として現れる。
- AC-05: 同一セッションで問診は最大2回。連続ターンでは発火しない。
- AC-06: 問診回答に「喉が痛い」を含むと、返答が練習継続でなく休声・受診目安の案内になり、そのセッションで高負荷練習を提案しない。
- AC-07: アカウント削除でカルテも削除される。
- AC-08: カルテ更新系の障害（DB書込失敗）が起きてもFB本文は返る。
- AC-09: 前回から30日以上空いたセッションでは宿題の確認ではなく再開の挨拶になる。
- AC-10: 開始挨拶はいかなるモードでも宿題・練習名に言及しない。カルテの宿題として保持・参照される練習名は、過去の会話（ユーザー発言より後のコーチ発言）に実際に登場したものに限り、登場していない宿題はセッション開始時に破棄される。

## 8. 前提・制約
- `User` は最小（email のみ）、セッション状態は `ChatSession` 単位（backend/app/models/coaching.py）。カルテは新テーブル（user_id 一意）＋Alembicマイグレーションが必要。
- 問診の回答は自由文（専用UIなし）。既存のテキストチャット経路に乗せる。
- docs/42（ペルソナ・作法）は不変。カルテは「事実供給」の拡張であり、語り口は変えない。

## 9. 未決事項 / 要確認
- Q1: カルテをユーザーに見せるか（マイページ「あなたのカルテ」）。→ MVP外。反応を見て designer 案件化。

- Q3: 無料/有料でカルテ機能に差をつけるか（例: 主観メモ履歴の長さ）。→ MVPは差なし。転換レバーにするかは CEO 判断待ち。

## 1. システム構成

```
[frontend 登録フォーム]
   → POST /api/v1/auth/register (backend)
        ├─ ユーザー作成 + commit（既存処理・変更なし）
        ├─ BackgroundTasks.add_task(send_welcome_email, user_id, email)
        └─ 201 返却（メール送信を待たない）
              ↓ レスポンス返却後にバックグラウンド実行
        [mail_service] ── HTTPS POST ──> [Brevo API] ──> ユーザーの受信箱
```

- 新規コンポーネントは `backend/app/services/mail_service.py` のみ。DB変更なし、フロント変更なし。

## 2. アーキテクチャ判断

### 2.1 メールAPI選定: Brevo（REST API）

**制約が選定を支配する**: 本番ドメインは `sora-vocal-ai.duckdns.org`（DuckDNS）。DuckDNSはTXTレコードを実質1本しか持てず、SPF＋DKIM（selector._domainkey）の複数TXTを要求する「独自ドメイン認証」が構成できない。したがって**ドメイン認証必須のプロバイダは選択肢から外れる**。

| プロバイダ | 無料枠 | ドメイン認証なしで送信可 | 判定 |
| --- | --- | --- | --- |
| **Brevo** | **300通/日（恒久）** | **可（送信者メール認証のみ）** | **採用** |
| SendGrid | 100通/日（恒久） | 可（Single Sender Verification） | 次点 |
| Resend | 3,000通/月 | 不可（独自ドメイン認証必須） | 除外（DuckDNS制約） |
| Amazon SES | 実質有料化（EC2外） | 不可＋本番申請が重い | 除外 |
| Mailgun | 無料枠廃止（トライアルのみ） | — | 除外 |
| Gmail SMTP | 500通/日 | 可（自分のアカウント） | 代替案（§2.3） |

- Brevo採用理由: 無料枠が最大（300通/日 ≒ 9,000通/月、要件の月間登録数<100人の90倍）、送信者アドレスの確認リンククリックだけで送信開始できる、REST APIが単純（APIキーのヘッダ＋JSON 1回のPOST）。
- 送信者アドレス: 運用者のGmail（またはBrevoで確認できる任意のアドレス）を送信者として登録する。DKIMはBrevoドメイン署名になるため受信側で「via brevo」表示になり得るが、トランザクションメール1通の到達には実用上十分。
- **拡張ポイント**: 将来独自ドメイン（例: sora-vocal.com）を取得したら、Brevo管理画面でドメイン認証を足すだけで送信者ドメインを差し替えられる。コード変更は env の `MAIL_FROM_ADDRESS` のみ。

### 2.2 送信タイミング: FastAPI BackgroundTasks

- 検討した代替案:
  - (a) 同期送信 → 登録レスポンスが最大10秒遅延。US-02違反。却下。
  - (b) DBキュー＋cronバッチ（push_reminders方式）→ 再送・複数通に必要だが、1通のみ・再送なし（FR-01）の本件には過剰。却下。
  - (c) **BackgroundTasks** → レスポンス返却後に同一プロセスで実行。追加インフラゼロ、失敗隔離が自然にできる。**採用**。
- トレードオフ: プロセスが送信前に落ちるとメールは消失するが、FR-02（再送なし・ベストエフォート）の範囲内と判断。

### 2.3 代替案として却下: Gmail SMTP直送
アカウント追加不要・Google署名で到達性最良だが、(1) アプリパスワードという「人間の認証情報」を本番envに置くことになり漏洩時の影響範囲がGmailアカウント全体に及ぶ、(2) SMTPはブロッキングI/Oでタイムアウト制御が粗い。APIキー（権限がメール送信に限定・即失効可能）で済むBrevoを優先する。

### 2.4 HTTPクライアント: requests（明示追加）
- pywebpush 経由で transitively に入っているが、直接依存を requirements.txt に明示する（バージョン浮動の事故防止）。
- 検討した代替案: 標準ライブラリ urllib → タイムアウト・エラー処理の記述が冗長。httpx → 新規依存としては requests より重い。同期コンテキスト（BackgroundTasks はスレッド実行）なので requests で十分。

### mail_service.py の責務（push_sender.py のイディオムに揃える）

```python
logger = logging.getLogger("app.mail")

def mail_enabled() -> bool: ...        # settings.mail_enabled を参照

def send_welcome_email(user_id: int, to_email: str) -> None:
    """登録直後のウェルカムメールを1通送る。例外は外に漏らさない（FR-02）。"""
    # 1) 未設定なら logger.info("welcome mail skip（未設定） user_id=%s") で終了（FR-03/AC-05）
    # 2) 件名・本文を組み立て（docs/86 のテンプレ、CTA は settings.frontend_base_url ベース。FR-04/AC-06）
    # 3) Brevo API POST https://api.brevo.com/v3/smtp/email
    #    headers: {"api-key": settings.mail_api_key}
    #    body: {sender: {name, email}, to: [{email}], subject, textContent}
    #    timeout=settings.mail_timeout_sec（10秒。FR-02）
    # 4) 2xx → logger.info("welcome mail sent user_id=%s")
    #    それ以外/例外 → logger.warning(...)。raise しない
```

- 本文テンプレートは `mail_service.py` 内の定数（`WELCOME_SUBJECT` / `WELCOME_BODY`）。正本は docs/86 で、変更時は両方更新（docs/42 の単一ソース運用と同じ規律）。
- プレーンテキストのみ（HTMLなし）。トランザクションメール1通にHTMLは過剰で、スパム判定リスクも下がる。

## 7. エラーハンドリング方針
- `send_welcome_email` は**いかなる例外も外に伝播させない**（try/except Exception で捕捉→warning ログ）。BackgroundTasks 内の例外はレスポンスに影響しないが、ログを汚さないためにも関数内で完結させる。
- リトライなし（FR-01）。Brevo側の4xx（キー無効等）も warning ログのみ。
- ログにはメール本文・APIキーを出さない。宛先は user_id で追跡（FR-05）。

## 8. 性能・可用性考慮
- 登録レスポンスへの影響: BackgroundTasks はレスポンス送出後に実行されるため 0ms。
- Brevo 障害時: タイムアウト10秒で打ち切り、warning ログ。登録機能は無傷（AC-03）。
- 無料枠超過（300通/日）: Brevo が 4xx を返す → warning ログのみ。現状の登録ペースでは到達しない。

## 9. セキュリティ考慮
- APIキーは env（`MAIL_API_KEY`）のみ。リポジトリ・ログに出さない。本番は VPS の docker/.env に運用者が設定。
- 送信先は DB に保存された登録済み email のみ。外部入力から宛先を組み立てない。
- CTA リンクは `frontend_base_url` からサーバー側で生成（ユーザー入力を含めない）。

## 10. テスト方針（QAと連携）
- 単体: `mail_service.send_welcome_email` を requests をモックして検証（成功/4xx/例外/未設定スキップ）。
- 結合: `POST /register` で (1) add_task が呼ばれる（モック）、(2) メール無効でも 201、(3) 送信例外でも 201、(4) 重複400で送信されない。
- 実送信テストはQA範囲外（運用者がキー設定後に自分のアドレスで1回確認する手順を docs/86 に記載）。

## 11. 移行 / 後方互換性
- env 未設定のままデプロイ可能（FR-03: 完全に現行動作）。マイグレーション不要。ロールバックはコード revert のみ。
- 運用者作業（キー取得後）:
  1. Brevo アカウント作成 → 送信者アドレス認証 → APIキー発行（運用者自身の作業）
  2. VPS の `/opt/vocalcoach/docker/.env` に `MAIL_API_KEY` と `MAIL_FROM_ADDRESS` を追記
  3. `docker compose -f docker-compose.prod.yml --env-file .env up -d backend` で backend 再起動

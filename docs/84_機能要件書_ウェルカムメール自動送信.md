# ウェルカムメール自動送信 機能要件書

- 文書番号: 84
- 作成日: 2026-08-01
- 作成: PdM
- 関連: docs/01（要件定義）, docs/42（FB品質基準・ソラ先生人格の正本）, docs/17（LPコピー）, docs/86（メール文面・本件成果物）

## 1. 概要
- 新規ユーザー登録が完了した直後に、ウェルカムメールを1通だけ自動送信する。
- 解決する課題: 登録したまま初回録音に進まないユーザーの離脱。現状は登録後のフォローが一切なく、初回体験（ソラ先生のFBを1回受ける）への導線がLP上にしかない。

## 2. 想定ユーザー / ユースケース
- ペルソナ: 声診断やLP経由で登録した直後のユーザー。まだ録音を1本もアップロードしていない。
- 主要ユースケース:
  1. ユーザーが登録を完了する → 数分以内にウェルカムメールが届く → メール内CTAから録音ページへ戻り、初回録音を行う。

## 3. スコープ
### 3.1 対象（やること）
- 登録完了時のウェルカムメール1通の自動送信（トランザクションメール）
- 送信の有効/無効を環境変数で制御（キー未設定なら送信スキップ＝現行動作）
- 送信結果（成功/失敗）のアプリケーションログ出力

### 3.2 対象外（やらないこと）
- 週次・定期メルマガ、ステップメール（2通目以降）
- 配信リスト管理・購読解除管理のUI（本件は登録に付随する1通のみで、広告目的の継続配信ではない）
- 送信履歴のDB保存、開封率・クリック率の計測
- メールアドレスの到達性検証（バウンス処理）
- 管理画面からの文面編集（文面はコード内テンプレート、正本は docs/86）

## 4. ユーザーストーリー
- US-01: 登録直後のユーザーとして、次に何をすればいいかをメールで受け取りたい。なぜなら登録しただけではサービスの価値（ソラ先生のFB）を体験できていないから。
- US-02: 運用者として、メールAPIの障害が本体機能（登録）に影響しないでほしい。なぜなら登録はプロダクトの生命線だから。
- US-03: 運用者として、メール基盤の月額コストを0円に保ちたい。なぜなら現在の登録ボリュームでは有料プランを正当化できないから。

## 5. 機能要件

### FR-01: 登録完了時の自動送信
- 概要: `POST /api/v1/auth/register` が成功（201）した時、登録メールアドレス宛にウェルカムメールを1通送信する。
- 詳細仕様:
  - 送信はレスポンス返却をブロックしない（非同期実行）。
  - 送信対象は登録成功したユーザーのみ。既存メール重複での 400 時は送信しない。
  - 1ユーザーにつき送信は登録時の1回のみ。再送機構は持たない。
- 入出力: 入力＝登録ユーザーのemail。出力＝メール送信（件名・本文は docs/86 に従う）。
- 例外ケース: 送信API障害・タイムアウト時も登録レスポンスは 201 のまま（FR-02）。

### FR-02: 送信失敗の隔離
- 概要: メール送信の失敗は登録処理に一切影響しない。
- 詳細仕様:
  - 送信処理内の例外はすべて捕捉し、エラーログを出して終了する（リトライなし）。
  - 送信タイムアウトは10秒以内に打ち切る。

### FR-03: 環境変数による有効化制御
- 概要: メールAPIキー等の設定が揃っている時だけ送信する。未設定なら送信をスキップし、現行動作（メールなし）と完全に同一。
- 詳細仕様:
  - 有効判定は既存の `llm_enabled` / `push_enabled` と同様の property パターンで実装する。
  - 無効時はログに「skip（未設定）」を1行出す（デバッグ可能性のため）。

### FR-04: 文面
- 概要: 件名・本文は docs/86_メール文面_ウェルカム便.md を正本とする。
- 詳細仕様:
  - 差出人はソラ先生名義（人格・トーンは docs/42 準拠）。
  - CTAは1つだけ（初回録音ページへのリンク）。リンク先は `frontend_base_url` を基準に生成する。
  - 特定電子メール法への配慮: 送信者名義・運営者の連絡先（メールアドレス）を本文フッターに明記する。本メールは登録に付随する通知（トランザクションメール）であり広告宣伝メールに該当しない構成とする。

### FR-05: 送信結果のログ
- 概要: 成功・失敗・スキップをアプリケーションログに出力する。
- 詳細仕様: ログにはユーザーIDと送信結果を含める。メール本文はログに出さない。

## 6. 非機能要件
- コスト: 月額固定費0円（無料枠のあるメールAPIを使用）。無料枠は現実の登録ペース（当面 <100人/月）の10倍以上の余裕があること。
- 性能: 登録レスポンスのレイテンシ増加は実測で体感差なし（非同期実行のため原理上ほぼ0）。
- セキュリティ: APIキーは環境変数（VPSは docker/.env）でのみ保持。リポジトリにコミットしない。
- 保守性: 送信サービスは独立モジュール（`backend/app/services/` 配下）とし、将来のメール種別追加（リマインド等）で再利用できる形にする。
- 到達性: 独自ドメインからの送信が無料枠で可能なプロバイダを優先（SPF/DKIM設定可能であること）。

## 7. 受け入れ基準
- AC-01: メール設定が有効な状態で登録すると、登録メールアドレスにウェルカムメールが1通届く。
- AC-02: メール設定が未設定の状態で登録しても、登録は成功し、エラーは発生しない（現行動作と同一）。
- AC-03: メール送信APIが失敗（例外・タイムアウト）しても、登録APIは 201 を返す。
- AC-04: 重複メールでの登録失敗（400）時、メールは送信されない。
- AC-05: 送信成功・失敗・スキップがそれぞれログで確認できる。
- AC-06: メール本文のCTAリンクが `frontend_base_url` 設定に追随する（ハードコードしない）。

## 8. 前提・制約
- メールAPIのアカウント作成・APIキー発行・ドメイン認証（SPF/DKIM）は運用者（丸山さん）の作業。Claudeは代行できない。
- キー未設定の間、本機能は自動的に無効（FR-03）。したがって本実装はキー取得前にマージ可能。
- プロバイダ選定（無料枠比較）はアーキテクトが docs/85 で決定する。

## 9. 未決事項 / 要確認
- 送信元アドレス（例: sora@<独自ドメイン>）のドメイン運用者確認 → 設計時にアーキテクトが現行ドメイン構成を確認して提案。
- 将来ステップメール化する場合は購読解除の仕組みが必須になる（本件スコープ外の申し送り）。

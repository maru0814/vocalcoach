## 1. 概要
- **一言**: Xで「歌の悩みを実況している人」を見つけて絞り込み、**フォローすべき人だけ**をLINEに一覧で毎日届け、**フォロー実行は人間がXアプリで行う**半自動パイプライン。
- **解決する課題**: フォロワーを増やしたいが、無差別フォロー連射は **Xのスパム検知（platform manipulation）でバンされる**。手動運用は「誰をフォローすべきか探す」工程が重く続かない。この探索・選別だけを自動化し、**フォローを撃つ最後の一押しは人間が持つ**ことで、バンリスクを上げずに手間を減らす。

### 背景（現状分析の要点）
- 既存 `scripts/sns_autopost` に **投稿の自動化パイプライン**が完成済み: `生成 → 専門家ゲート(expert_review.py) → LINE承認(webhook.py/line_client.py) → X投稿(generate_and_post.py) → 計測(fetch_metrics.py)`。本機能はLINE通知・OAuth/レート管理・計測の枠組みを再利用する。
- **API課金の前提（2026年2月〜の従量課金）**: post read **$0.005/件**・user read **$0.010/件**・owned read（自投稿/自フォロワー等）**$0.001/件**・24時間の同一リソース重複排除あり。探索read は**日次予算ガード（既定 $0.60/日）**の範囲でAPIを使う。
- **フォロー自動化は恒久的に不採用（一次原理）**: Xの自動化ポリシーはフォロー/アンフォローの**大量・機械的な実行そのもの**を禁止行為として明記しており、これは「人間がボタンを1回押しただけか」とは無関係。LINEに一括フォローボタンを置いてAPI側でN件連続フォローする設計にしても、規約上のリスクは一切下がらない。したがって**フォローの実行はAPIを一切経由せず、常にXアプリ上で運用者本人の指で行う**。
- 2026-07-06の方針転換後、返信文生成（旧`lead_reply.py`）・返信用専門家ゲート（旧`expert_review.review_lead_reply`）は**廃止・削除済み**。歌手名のでっち上げリスクや返信トーンの管理コストごと解消された。

## 2. 想定ユーザー / ユースケース
- **ペルソナ（運用者）**: 丸山（1人運用）。X/LINEを日常的に使う。API課金と規約違反を最も恐れる。1日に割ける運用時間は10分以内。
- **フォロー候補（狙う相手）**: 歌の悩みを**今まさに言語化している非プロ層**。例「高音が出ない」「換声点で裏返る」「ミックスボイスできない」「歌の音痴を直したい」「精密採点◯点だった」。フォロワー数 数十〜数千の伸び悩み層。
- **主要ユースケース**:
  1. 1日1回、システムが候補（相手のプロフィール要約＋元ツイート抜粋＋プロフィールリンク）をLINEに一覧で届ける。
  2. 運用者はリンクをタップしてXアプリで対象を確認し、**気になる人を自分の指でフォロー**する（＝API課金ゼロ・行為は人間）。
  3. 一覧の対応が終わったら [✅全員フォローした] を1回押す（実施の自己申告記録。X APIは呼ばれない）。
  4. 後日、フォロー実施リードのフォロバ有無を計測し、勝ちクエリ/負けクエリを可視化する。

## 3. スコープ

### 3.1 対象（やること）
- **保存クエリ集**（悩み実況層を捕まえる検索文）の管理（`themes.py` と同様のコード内SSOT）。
- **候補の選別基準**（フォロワー数レンジ・言語・文脈・bot/相互除外・重複除外）の定義。
- **LINEダイジェスト**: 1日分の候補（プロフィール要約・元ツイート抜粋・プロフィールリンク）を一覧表示し、末尾に [✅全員フォローした][⏭今回は見送る] ボタンを1組だけ出す。
- **実行上限のコード固定**: 1日あたり提示件数の上限（既定 `MAX_FOLLOWS_PER_DAY=15`）。公式な安全値は存在しないため、フォロー速度スパイクを避ける経験則に基づく初期値とし、運用実績で調整する。
- **計測**: 提示・フォロー実施の記録（`engaged_log.jsonl`）と、クエリ別フォロバ率の集計。

### 3.2 対象外（やらないこと）
- **X API経由の自動フォロー実行**（ボタン起点の一括実行を含む。＝バン主因。恒久的に対象外）。
- **返信文の生成・提案**（2026-07-06付けで廃止。返信するかどうか・内容は運用者の自由）。
- **read課金の青天井利用**（探索readは日次予算ガード内のみ）。
- 相手ツイートの**大量スクレイピング**（規約リスク）。入力は運用者操作を起点とした最小取得に限る（§8）。
- DM送信の自動化。
- Instagram/TikTok等X以外のSNS。
- フォロー数の**ノルマ化**（上限は「これ以上は危険」の天井であり、毎日埋める目標ではない）。

## 4. ユーザーストーリー
- **US-01**: 運用者として、歌の悩みを実況している人を毎回自分で検索しなくても、フォローすべき候補が一覧でLINEに届いてほしい。なぜなら探す工程が一番だるいから。
- **US-02**: 運用者として、機械が勝手にフォローを実行しないでほしい。なぜならバンされたら資産ごと失うから。最後は自分の指で押したい。
- **US-03**: 運用者として、対応が終わったら1回のタップで「今日の分は済んだ」と記録したい。なぜなら1人ずつ確認応答するのは面倒だから。
- **US-04**: 運用者として、どの検索クエリが実際にフォロバに繋がったか知りたい。なぜなら効くクエリに絞って無駄打ちを減らしたいから。
- **US-05**: 運用者として、1日にどれくらいフォローして安全か目安がほしい。なぜなら自己判断だとやり過ぎて不安になるから。

## 5. 機能要件

### FR-01: 保存クエリ集（探索クエリのSSOT）
- **概要**: 悩み実況層を捕まえる検索文を、コード内の単一ソースで管理する。
- **詳細仕様**:
  - `LEAD_QUERIES: list[dict]` （`themes.TIPS` と同形式）。各要素は `{"id", "query", "intent", "keywords", "require"?}`。
  - 初期セットは10クエリ（高音/換声点/ミックス/音痴/音程不安定/精密採点/裏声/喉声/ロングトーン/歌ってみた）＋エンゲージ起点(`mention`)。
  - 曖昧クエリ（例: 「音痴」は方向音痴等の非歌唱文脈を大量に含む）には `require`（歌文脈語のいずれか必須）と `NEGATIVE_COMPOUNDS`（非歌唱の複合語を即除外）を設ける。**2026-07-05初回本番実行で実際に必要性が確認された**（「音痴 直したい」検索の通過10件中8件が歌と無関係だった）。
  - クエリ改定は growth-operator が §7の計測を見て行う。
- **入出力**: 入力＝なし（静的定義）。出力＝クエリ配列。
- **例外**: クエリが0件になる設定はロード時に検知しエラー終了（無音運用防止）。

### FR-02: 候補の選別基準（"絞る"の本体）
- **概要**: 取得した候補ツイート/ユーザーから、フォローすべき候補だけに絞る。
- **詳細仕様（判定条件、すべてANDで通過）**:
  - **言語**: 日本語（本文が主に日本語）。
  - **文脈**: 本文がクエリのintent/keywordsに合致し、曖昧クエリは`require`語を含む。`NEGATIVE_COMPOUNDS`（方向音痴・機械音痴等）を含む本文は除外。
  - **フォロワー数**: 既定レンジ `LEAD_FOLLOWERS_MIN=30` 〜 `LEAD_FOLLOWERS_MAX=3000`（伸び悩み・上達意欲層。プロ/バズ済みを除外）。取得できない候補は本条件をスキップ。
  - **bot/相互フォロー目的の除外**: プロフィールに「相互」「フォロバ100%」等の相互狙いワードを含む候補は除外（`LEAD_EXCLUDE_KEYWORDS`）。
  - **重複除外**: 既に `engaged_log.jsonl` に記録済み（提示済み）のユーザーは再提示しない。
- **入出力**: 入力＝候補（相手ツイートID/本文・ユーザーのフォロワー数/プロフ）。出力＝通過候補配列（最大 `MAX_FOLLOWS_PER_DAY`）。
- **例外**: 通過0件なら「本日は該当なし」をLINE通知し正常終了（エラーにしない）。

### FR-03: エンゲージ起点候補（最優先ソース）
- **概要**: 自分の投稿にリプ/メンションしてきたユーザーを最優先の候補にする。
- **詳細仕様**: owned read（≒$0.001/件）で自投稿へのメンションを取得。すでに興味を示した相手なので文脈intent判定はスキップし、他の選別（相互除外・重複・フォロワーレンジ）は適用する。候補収集の優先順は「ペースト入力→メンション→API検索」（安い順）。
- **例外**: メンション0件・API不可時は他ソースにフォールバック（エラーにしない）。

### FR-04: read課金の日次予算ガード
- **概要**: 探索のread課金が暴走しないよう、日次概算予算をコードで固定する。
- **詳細仕様**: `LEAD_DAILY_READ_BUDGET_USD`（既定 0.60）。post read $0.005 / user read $0.010 / owned read $0.001 で概算し、`lead_reads_log.jsonl` に日別累計を記録。当日累計が予算に達したら以降の検索・lookupを停止する。user readは**本文選別を通過した候補のみ**に実行する（遅延lookup）。
- **例外**: 予算消化済みで起動された場合は探索せず正常終了。

### FR-05: LINEフォロー候補ダイジェスト（半自動の要）
- **概要**: 1日分の候補を一覧メッセージで届け、対応完了を1回のタップで記録する。
- **詳細仕様**:
  - 候補ごとに **①ハンドル名 ②フォロワー数 ③選定理由（クエリのintent） ④元ツイート抜粋 ⑤プロフィール/ツイートURL** を1行にまとめて表示。返信文は含めない。
  - 候補数が多い日でもLINEの1push上限（5メッセージ）に収まるよう、候補一覧を複数メッセージにチャンク分割し、末尾に確認ボタンを1組だけ置く。
  - ボタンは `webhook.py` の postback（`act=lead_followed_batch|lead_skip_batch`、対象はその日のバッチID）。
  - **[✅全員フォローした]** 押下で **X APIは叩かず**、当該バッチの候補すべてを `engaged_log.jsonl` 上で `status=followed` に更新する（＝フォロー実施の自己申告記録のみ）。
  - **[⏭今回は見送る]** 押下で当該バッチを `skipped` に更新（次回以降は再提示しない＝対応済み扱い）。
  - 1日の提示上限 `MAX_FOLLOWS_PER_DAY` をコードで固定。
- **入出力**: 入力＝通過候補一覧。出力＝LINEメッセージ／postback処理結果。
- **例外**: LINE未設定時はDRY_RUN扱いで標準出力に候補一覧を表示（投稿系と同じ安全側）。

### FR-06: 計測（フォロバ率の可視化）
- **概要**: フォロー実施済み候補のその後（フォロバ有無）を集計し、クエリ別の効果を出す。
- **詳細仕様**:
  - `engaged_log.jsonl` に `{lead_id, handle, query_id, followers, source_text, url, batch_id, status, suggested_at, followed_back}` を記録。`status` は `suggested|followed|skipped`。
  - 週次実行の集計スクリプトが、`status=followed` の候補ごとに **フォロバされたか**（＝そのユーザーが自アカウントをフォローしているか）を確認し、`query_id` 別のフォロバ率を出す。
  - フォロバ確認は自分のフォロワー一覧の取得（自アカウント読取＝低コスト）で行い、他人ツイート検索の有料APIは使わない。
- **入出力**: 入力＝`engaged_log.jsonl` ＋ 自フォロワー一覧。出力＝クエリ別フォロバ率レポート（標準出力）。
- **例外**: フォロワー取得APIが使えない環境では「計測スキップ」を明示（探索・提示自体は動く）。

## 6. 非機能要件
- **バン安全性（最重要）**: X APIを介した能動的なフォロー/DMの**自動実行を一切行わない**。実行は常に人間の手タップ。API利用はread（検索・user lookup・自アカウント読取）に限定する。
- **フォロー数の目安（公式な保証値ではない）**: 新規/小規模アカウントは最初の1〜2週間は10〜15件/日、様子を見て段階的に25件程度まで。1日分を数分で一気にタップせず時間を分けて行う（フォロー速度のスパイクが検知されやすいため）。既定 `MAX_FOLLOWS_PER_DAY=15` はこの経験則の初期値。
- **コスト**: 探索readは日次予算ガード内（既定 $0.60/日 ＝ 月上限 ≒$18）。24時間重複排除と遅延lookupで実コストはさらに下がる。返信生成・専門家ゲートの廃止によりGemini課金は発生しない。運用者ペースト方式（oEmbed）は¥0で併用可。
- **安全側デフォルト**: キー未設定/`DRY_RUN=1` では記録・LINE送信をせず候補表示のみ。
- **保守性**: 既存 `sns_autopost` の構成・命名・env規約を踏襲。SSOT（クエリ）はコード内単一ソース。
- **UX**: LINE1回のpushで1日分の意思決定が完結（末尾ボタン1組）。運用者の1日の所要は10分以内。

## 7. 受け入れ基準
- **AC-01**: `DRY_RUN=1` で実行すると、LINE送信・`engaged_log`書き込みを一切せず、通過候補一覧が標準出力に表示される（Yes/No）。
- **AC-02**: 選別基準（言語/文脈/フォロワー数レンジ/相互ワード除外/重複除外/非歌唱複合語除外）のいずれかに外れる候補が、出力候補に含まれない（Yes/No）。
- **AC-03**: LINEダイジェストの本文に返信文・返信案に相当する記述が含まれない（Yes/No）。
- **AC-04**: 1回の実行でLINEに提示される候補数が `MAX_FOLLOWS_PER_DAY`（既定15）を超えない（Yes/No）。
- **AC-05**: LINEで [✅全員フォローした] を押しても **X APIへのフォロー呼び出しが発生せず**、対象バッチの `engaged_log.jsonl` が `status=followed` に更新される（Yes/No）。
- **AC-06**: 通過候補0件のとき、エラーではなく「本日は該当なし」通知で正常終了する（Yes/No）。
- **AC-07**: 計測スクリプトが `status=followed` の候補のみを対象に `query_id` 別のフォロバ率を出力し、`engaged_log` に無いユーザーが集計に混入しない（Yes/No）。
- **AC-08**: [⏭今回は見送る] は該当バッチのみを更新し、他バッチ・他日の候補に影響しない（Yes/No）。

## 8. 前提・制約
- **入力方式（安い順に3ソース併用）**:
  1. **運用者ペースト方式**（¥0）: XアプリでのURL目視ペースト → oEmbed（無認証）で本文取得。API不調時のフォールバックとしても機能。
  2. **エンゲージ起点**（owned read ≒$0.001/件）: 自投稿へのメンション/リプ（FR-03）。
  3. **従量API検索**（post read $0.005/件＋通過分のみ user read $0.010/件）: `leads.LEAD_QUERIES` を日替わりローテーション（FR-04 の予算内）。
- **バン方針**: 1日の提示上限・重複除外・相互狙い除外をコードで固定。フォロー実行はすべて人間の手動。**write自動化は恒久的に対象外**（一括確認ボタンもX APIを呼ばない）。
- **既存資産の再利用**: LINE通知(`webhook.py`/`line_client.py`)・OAuth/計測(`fetch_metrics.py`)を流用し、新規実装を最小化する。

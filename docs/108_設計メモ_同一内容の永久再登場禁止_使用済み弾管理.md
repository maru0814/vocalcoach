# 108. 設計メモ — 同一内容の永久再登場禁止（使用済み弾管理）

- 作成: 2026-08-17 / 担当: グロースオペレーター
- 対象: `scripts/sns_autopost/`（dedup.py 新設 / themes.py / generate_and_post.py / webhook.py / backfill_used_ammo.py）
- 依頼: 「一度作ったツイートと同じ内容は絶対に未来永劫でないようにして」（運用者）
- 前提: docs/107（通算出番ローテ）。107は「再登場の間隔を最大化」だったが、本件で
  「一巡したら繰り返す」設計自体を廃止し、**再利用ゼロ**に変える。

## 1. 保証の構造（3層）

### 層1: 使用済み弾の永久除外（生成時）
- 弾（themes のテンプレ下敷き）ごとに指紋 **ammo_key**（pillar＋本文＋リプ本体のsha1）を持つ。
- 下書きを承認キューに積んだ時点でレコードに ammo_key を記録（却下・保留になった弾も
  「作った」とみなし再利用しない）。
- 弾選び `dedup.pick_unused_index()` は、ローテ位置（docs/107 の通算出番）を起点に
  **未使用の弾だけ**を選ぶ。全弾使用済みなら None（＝弾切れ）。
- 弾の文言を改稿すると ammo_key が変わり「新しい弾」になる（意図どおり）。

### 層2: 弾切れ時は新作生成、できなければ見送り
- tip / contrarian: `themes.gemini_fresh_twopart_prompt()` — 過去に作ったテーマの
  一覧（キュー履歴の本文1行目）を除外リストとして渡し、**新しいテーマ**の2部構成を
  Gemini に書かせる。内容の鉄則（定説の範囲・喉を痛める練習の禁止・誇張禁止・実名を
  出さない）をプロンプトに明記。専門家ゲート（expert_review）は通常どおり通す。
- 診断導線（self_type / voice_type / visual）: 早見リプは正本のまま、フックだけ
  過去フック一覧を除外して新作（`gemini_diagnosis_hook_prompt(avoid=...)`）。
  ※通常生成時も avoid を常時渡し、過去フックと似た文面を避ける。
- artist_analysis: **新作の自動生成はしない**（実名のでっち上げ禁止・docs/84）。
  弾切れは見送り＋LINE通知（`themes.py` への補充は人間監修の週次運用）。
- 新作も作れない（Gemini未設定・失敗）場合: **その枠は投稿を見送り**、LINEに
  「弾切れ・補充が必要」を通知する。**同じ内容を出すくらいなら出さない**。

### 層3: 投稿直前の最終ゲート（絶対の保証）
- 投稿された本文の指紋 **text_hash**（空白揺れを吸収したsha1）を記録。
- 投稿が起きる全経路（webhook の承認処理 / `--post-now`）で、投稿直前に
  `dedup.is_posted_duplicate()` を通し、**過去に投稿済みと同文なら投稿しない**。
  webhook では自動却下し、LINEに「二重投稿防止」と返信する。
- これにより、同文の下書きがキューに複数残っていて両方承認されても2件目は止まる
  （2026-08-17 に実際に起きかけたケース: 同文のカード版/図解版が両方 pending になった）。
- `--text`（完成稿の手動投入）も、投稿済みと同文なら受け付けない（rc=2）。

## 2. 記録の置き場（新しい状態ファイルは最小限）
- ammo_key / text_hash は既存の `pending_queue.jsonl` / `posts_log.jsonl` のレコードに
  フィールド追加。過去レコード（指紋なし）は status=posted の text から都度計算して
  後方互換で取り込む。
- 例外は `used_ammo.jsonl`（追記専用・バックフィル用）のみ。

## 3. 過去分のバックフィル（`backfill_used_ammo.py`）
ammo_key 導入前に使われた弾は記録が無く「未使用」に見えるため、キュー履歴と現行弾倉を
突き合わせて焼却記録する。誤って未使用の良弾を焼かないよう**確実な一致のみ**:
1. 本文の完全一致（テンプレ素のまま出た過去分）
2. リプ本体の完全一致（フックだけリライトされた過去分）
3. 本文1行目の完全一致
4. artist_analysis のみ実名一致（実名は弾ごとに一意・他歌手名の追加は禁止のため安全）

既定は dry-run。SNS Ops ワークフローの `backfill-ammo-dry` / `backfill-ammo` で
本番実行する（**本PRのデプロイ後に一度実行すること**）。

### 限界の明示（事実忠実性）
- Gemini がリライトした過去分のうち、上記ルールで一致しないもの（本文もリプも1行目も
  別文言）はバックフィルで特定できない。その弾は**最大1回**新しい文面で再登場しうる
  （文面の完全一致は層3で常に遮断される）。以後は ammo_key が記録され永久に出ない。
- 「同じ内容」の意味は、弾レベル＝同じ下敷き（層1）と、本文レベル＝同じ文面（層3）で
  厳密に定義した。意味がほぼ同じで文面が違う新作（Gemini生成）の重複は、除外リスト
  注入と専門家ゲートで抑制する（完全な意味的重複検知は行わない）。

## 4. 運用への影響
- 弾は消耗品になった。**週次運用（growth-operator）の弾補充が前提**:
  現在の弾数と消費ペース（週次出番）から、tip 約2.4週 / contrarian 2週 /
  voice_type 2週 / self_type 1.25週 / visual 1.5週 / artist_analysis 5週で
  テンプレ弾が尽き、以後は新作生成モード（artist_analysis は見送り）になる。
  週次レポートで残弾数を確認し、themes.py 末尾に弾を追加していく。
- 弾切れ見送りが起きると 1日3投稿を下回る。LINE通知が来たら補充が最優先。

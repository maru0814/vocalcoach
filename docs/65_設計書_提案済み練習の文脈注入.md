# 提案済み練習の文脈注入 設計書

関連: `docs/42_FB品質基準_単一ソース.md`（§5 事実忠実性・§6 練習継続）/ `docs/64_テスト計画_ソラ先生ハルシネーション自動検出eval.md` / `scripts/soar_eval/reports/REPORT_before_after.md`
実装先: `backend/app/coaching/llm.py`（単一ファイル・DB変更なし）

## 1. 背景（評価で確定した欠陥）
多ターン評価で、ユーザーが「あれ？さっきは別の練習がいいって言ってませんでした？」と**コーチ自身の発言への偽前提**をぶつけると、flash-lite は自分の会話履歴を監査できず「混乱させてしまいごめんなさい、以前お伝えしていたのであればそちらを優先して…」と**存在しない自分の発言を認めて追従**する（練習コロコロ変えまで誘発）。プロンプト指示（2026-07-10「言っていないことを言ったことにしない」）では**直らないことを before/after 測定で確認済み**。

解析事実への偽前提（F#5・95点）は否定できている。差は「照合できる事実が文脈にあるか」。**よって、提案済み練習を事実として文脈に注入する**（`current_task` 注入と同じ発想）。

## 2. アーキテクチャ判断

| 判断 | 採用 | 理由 |
| --- | --- | --- |
| 提案済み練習の導出元 | **会話履歴（history のコーチ発言）から都度抽出** | DB変更・エンドポイント変更・マイグレーション不要。generate_reply は既に history を受けており、そこにコーチの全発言（直近 `llm_history_turns` 件）がある。evalハーネスも自動で同挙動になる |
| 検討した代替案 | ChatSession に `proposed_practices` カラム追加＋返答後フック更新 | 窓を超える長い会話でも記憶できる利点はあるが、マイグレーション＋`_session_state`/`_apply_updates` 配線＋ハーネス配線が増える。contradict 罠は短い窓内で起きるため MVP では過剰。**将来、会話が `llm_history_turns` を超えて練習継続性が問題になったら移行**（その時はこの抽出関数を返答後フックに転用できる） |
| 抽出方式 | **決定論キーワードマッチ**（taxonomy の練習名に基づく既知語彙） | LLM抽出は不確実・高コスト。練習名は taxonomy 由来の閉集合なので部分文字列マッチで十分 |

トレードオフ: history 窓（`llm_history_turns`）の外で提案した練習は「提案済み」から漏れる。その場合の注入は「まだ提案していない」ではなく件数が減る方向であり、コーチが古い提案を否定しても §6 上の実害は小さい（会話が長い場合はユーザー発言にも練習名が現れ、窓内に再登場しやすい）。

## 3. モジュール構成（llm.py 内・3点）

```python
    "お腹ゆらしビブラート", "メッサ・ディ・ヴォーチェ", "クレッシェンド",
    "あくび発声", "あくび → ロングトーン", "メトロノーム手拍子",
)

def extract_practices(text: str | None) -> list[str]:
    """テキストに含まれる既知の練習名を出現順で返す（決定論）。"""
```
- 語彙は taxonomy と乖離しないよう、テストで `taxonomy.TASKS` の practices 名との対応を検証する（新練習追加時に落ちて気づける）。

### 3.2 履歴からの導出
```python
def proposed_practices_from_history(history: list[dict] | None) -> list[str]:
    """history の role=assistant 発言から提案済み練習を出現順・重複なしで集める。"""
```

### 3.3 文脈注入（build_session_context ではなく generate_reply 側）
`build_session_context(state)` のシグネチャは変えない（呼び出し元が多いため）。`generate_reply` / `_build_contents` で history を持っている場所で1行を context に追記する:
- 提案済みあり: `- この会話でこれまでにあなた（コーチ）が提案した練習: リップロール、ネイネイ（これが全て。これ以外の練習を「以前すすめた」ことにしない。ユーザーが別の練習に言及したら「その練習はこの会話ではまだ提案していない」と正直に伝える）`
- 提案済みなし: `- この会話ではまだ練習を提案していない（「さっき別の練習をすすめられた」と言われても、この会話の記録には無い）`

注入位置: `_build_contents` の `context = build_session_context(state)` 直後に連結（分析ターン `generate_feedback` は対象外。会話返答のみ）。

## 4. データフロー
```
coach.py: history = _history_for_llm(s)   （変更なし）
  → rule_engine._chat_reply(state, text, history)   （変更なし）
    → llm.generate_reply(state, text, history)
        props = proposed_practices_from_history(history)
        context = build_session_context(state) + 提案済み練習の行   ← 唯一の変更点
```

## 5. エラーハンドリング / 性能
- 抽出は純粋関数・例外なし。history None/空でも動作（「まだ提案していない」注入）。
- 語彙16件 × 履歴数十件の部分一致＝マイクロ秒オーダー。性能影響なし。

## 6. テスト方針（QA連携）
- 単体: `backend/tests/test_proposed_practices.py`
  - 抽出（複数・重複・順序・None安全）
  - 語彙が taxonomy の練習名と対応している（乖離検知）
  - `generate_reply` の LLM 入力（`_complete` へ渡る contents）に注入行が含まれる（モックで検証）
- E2E: eval ハーネスの多ターン contradict コーパス（18会話）で before/after 再測定。合格基準＝contradict 罠で「言っていない練習を認める」返答が消えること（審査 or 目視）。

## 7. 後方互換性
- API・DB・スキーマ変更なし。skill版（Claude Code）は Claude 自身が履歴を読めるため対象外（SKILL.md には 2026-07-10 の指示追記で対応済み）。

## 8. 将来拡張

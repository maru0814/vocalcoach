# 有料プラン（サブスク） 設計書

> アーキテクト作成（2026-06-12）。docs/31 要件書v2・docs/32 デザイン仕様に対応。
> 方針: 既存構成（FastAPI + SQLAlchemy + Alembic + Next.js）に最小追加。Stripeを真実の源泉とし、DBはそのキャッシュ。

## 1. 全体構成

```
Next.js ──▶ FastAPI /api/v1/billing/*  ──▶ Stripe (Checkout / Portal / API)
                 │  ▲
                 ▼  │ webhook (署名検証)
               MySQL: subscriptions / usage（既存: users, recordings, evaluations）
```

- プラン判定は**DBのみ参照**（リクエスト毎にStripeを呼ばない。webhookで同期）。
- 価格・Price IDはサーバ側 env（`STRIPE_PRICE_ID_PREMIUM`）。クライアントから金額を受けない。

## 2. DB設計（Alembicマイグレーション2件）

### 2.1 `subscriptions`
| 列 | 型 | 備考 |
| --- | --- | --- |
| id | BIGINT PK | |
| user_id | FK users.id, UNIQUE | 1ユーザー1行（最新状態のみ保持） |
| stripe_customer_id | VARCHAR(64), UNIQUE | |
| stripe_subscription_id | VARCHAR(64), UNIQUE | |
| status | VARCHAR(32) | Stripeの生値（active/trialing/past_due/canceled…） |
| current_period_end | DATETIME | |
| created_at / updated_at | DATETIME | |

判定関数（単一実装・全所から共用）:
`is_premium(user) = row.status in ('active','trialing') AND row.current_period_end > now()`

### 2.2 `usage_counters`
| 列 | 型 | 備考 |
| --- | --- | --- |
| id | BIGINT PK | |
| user_id | FK users.id | |
| yyyymm | CHAR(6) | JSTの暦月。UNIQUE(user_id, yyyymm) |
| analysis_count | INT DEFAULT 0 | 解析**完了**時にインクリメント |

- 月初リセットは行わない（月キー方式なので不要）。カウントアップは `INSERT ... ON DUPLICATE KEY UPDATE analysis_count = analysis_count + 1`（競合安全）。
- 履歴10件制限はカウンタ不要（一覧クエリの `LIMIT`/集約で表現）。

### 2.3 `evaluations` への追加
- `detailed_report` JSON NULL（生成済みレポート本体。4セクション構造）
- `report_generated_at` DATETIME NULL

## 3. API設計

| メソッド/パス | 認可 | 概要 |
| --- | --- | --- |
| `POST /api/v1/billing/checkout` | ログイン | Checkout Session作成（mode=subscription, price=env, client_reference_id=user_id, success/cancel URL）。既にpremiumなら409 |
| `POST /api/v1/billing/portal` | ログイン+加入歴 | Customer Portal Session URLを返す |
| `POST /api/v1/billing/webhook` | Stripe署名 | 下記4イベントを処理（§4） |
| `GET /api/v1/billing/me` | ログイン | `{plan: "free"/"premium", period_end, analysis_used, analysis_limit}`（S-01/S-05用） |
| `POST /api/v1/recordings/{id}/report` | ログイン+premium | レポート生成開始（生成済みなら200で即返す） |
| `GET /api/v1/recordings/{id}/report` | ログイン+premium+本人 | `{status: generating/ready/failed, report}` |

### 既存エンドポイントの変更
- `POST /api/v1/recordings`（解析開始）: 冒頭で `is_premium or analysis_count < FREE_ANALYSIS_LIMIT` を検査。超過は `402 LIMIT_REACHED`（フロントはS-02を開く）。解析**完了**処理の末尾でカウントアップ（失敗時は数えない＝FR-01）。
- `GET /api/v1/recordings`（一覧）: 無料ユーザーは最新10件＋`locked_count`（11件目以降の件数）を返す。**削除はしない**。

## 4. Stripe Webhook処理

| イベント | 処理 |
| --- | --- |
| `checkout.session.completed` | customer/subscription IDで `subscriptions` をUPSERT（client_reference_id→user_id） |
| `customer.subscription.updated` | status / current_period_end を更新（解約予約 cancel_at_period_end もここで来る） |
| `customer.subscription.deleted` | status='canceled' に更新 |
| `invoice.payment_failed` | 何もしない（subscription.updatedでpast_dueが来る。ログのみ） |

- 署名検証: `stripe.Webhook.construct_event`（`STRIPE_WEBHOOK_SECRET`）。失敗は400。
- 冪等性: イベントIDをログし、UPSERTベースなので再送安全。
- 順序逆転対策: `updated_at` より古い `current_period_end` での上書きはスキップしない（Stripe生値を信頼。statusはイベント時点の最新を採用）。

## 5. 詳細レポート生成

- トリガ: `POST /recordings/{id}/report`（オンデマンド。FR-04）。
- 入力: 該当 `evaluations` 行（pitch/rhythm/expression スコア＋解析詳細JSON）。出力: 4セクションの構造化JSON（スキーマをプロンプトで固定し、Pydanticで検証）。
- 生成: 既存のGemini呼び出し基盤を流用（`SNS_LLM_MODEL`と同系のテキストモデル）。検証失敗・API失敗はリトライ2回→`failed`。
- 同時実行ガード: `report_generated_at IS NOT NULL` なら再生成しない。生成中は `generating` 状態をDBの軽量フラグ（`detailed_report = {"_status":"generating"}`）で表現し、二重生成を防ぐ。
- 反ハルシネーション（docs/12）: プロンプトに「解析JSONに無い事実を述べない・データが薄い場合は『推定』と書く」を明記し、タイムスタンプは解析JSONの区間からのみ引用させる。

## 6. フロントエンド設計

- `lib/billing.ts`: `getBillingMe()` / `startCheckout()` / `openPortal()`。
- `useBilling()` フック（SWR）で plan/残回数を全画面共有。S-01バッジ・S-03ロック・S-04集約行はこれを参照。
- 新規ページ: `/billing/success`（60秒ポーリングで `billing/me` がpremiumになるまで待つ）・`/billing/cancel`・`/recordings/[id]/report`。
- 402 `LIMIT_REACHED` の共通ハンドラでS-02モーダルを開く（導線種別つき計測イベント送信）。

## 7. 設定（env追加）

```
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
STRIPE_PRICE_ID_PREMIUM=        # ¥800/月のPrice（金額の正本はStripe本番Price）
FREE_ANALYSIS_LIMIT=10
FREE_HISTORY_LIMIT=10
BILLING_ENABLED=1               # 0で全ゲート無効（緊急停止スイッチ）
```

- `BILLING_ENABLED=0` で従来どおり全機能無料（ロールバック手段。コードリバート不要）。

## 8. セキュリティ / 計測

- レポートAPIは本人＋premiumの二重チェック（AC-08）。
- 計測はバックエンドの構造化ログで実装（`event=paywall_view/click/checkout_start/subscribed/canceled, source=limit/report/history`）。集計はログのgrepで可能な形式（新規基盤を作らない）。

## 9. 実装順序（PR分割）

1. **PR-A** DB＋プラン判定＋利用上限ゲート（`BILLING_ENABLED=0`のままデプロイ可）
2. **PR-B** Stripe Checkout/Portal/Webhook（テストモードで検証）
3. **PR-C** 詳細レポート生成＋画面
4. **PR-D** 導線UI（S-01〜S-05）＋計測 → `BILLING_ENABLED=1` で公開

## 10. リスクと対応

- **webhook取りこぼし**（VPS再起動等）: `/billing/me` 取得時に `current_period_end` が過去かつ status=active の場合のみStripeへ1回照合する自己修復を入れる。
- **Stripe障害**: 判定はDBなので閲覧系は無影響。Checkoutのみ一時不可（許容）。
- **テスト**: Stripe CLIの `stripe listen --forward-to` でローカルwebhook検証。テストカード4242…でAC-03〜07を消化。

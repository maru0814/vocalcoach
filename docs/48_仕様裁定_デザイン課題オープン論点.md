## 0. 前提：現行IAの整理

| 入口 | 役割 | 録音→FBの形 | 課金との関係 |
| --- | --- | --- | --- |
| `coach`（会話型レッスン） | **継続のハブ**。曲決め→録音→会話FB→基礎練→再録音 | 会話型（チャット） | PremiumWidget で導線 |
| `voice-type`（声診断） | **集客の入口**。単発・シェア前提 | 単発診断 | 直接の課金面なし（送客） |
| `recordings`（旧・単発評価） | アップロード→4スコア評価→**詳細添削レポート（課金資産）** | 単発評価 | 詳細添削レポート＝有料の主価値 |

**核心の歪み**: 「録音→FB」が coach（会話型）と recordings（単発評価）に二重存在し、
ユーザーから見て「どっちで録ればいいのか」が不明。一方、課金の主価値（詳細添削レポート）は
畳みたい側の recordings にぶら下がっている。

---

## 1. 論点1【追認】声診断の認証ゲートの位置

- **決定**: **「未ログインで1回診断 → 結果ぼかし → シェア/保存で登録」を正とする**（登録必須にしない）。
- **根拠**: 声診断は docs/11 で集客の主役・US-01の入口。価値（自分の声タイプ）を見せる前の
  登録要求は入口KPI（登録率・診断完了率）を最も毀損する。
- **実装への落とし方**: PR #107 で実装済み（`analyze` 認証任意化・未登録はIP単位 rate limit、
  結果はぼかし＋登録CTA）。**docs/11 にトライアル動線を追記**（FR追加: 未登録は結果非開示・
  シェア/保存時に登録）。
- **影響範囲**: 濫用対策として IP rate limit を維持。将来 reCAPTCHA 等は別途検討（今はやらない）。

## 2. 論点4【最重要】主役の確定 — coach を中心に、recordings を畳む

- **決定**:
  1. **`coach` を単一の主役（中心）に確定**。録音→FBの正規ルートは会話型レッスン。
  2. **`recordings` の「アップロード→単発評価」入口は段階的に畳む**（新規導線をUIから外す）。
  3. ただし **詳細添削レポート（課金資産）は当面 `recordings/[id]/report` のまま残し**、
     coach の評価結果から渡す導線に付け替える（一気に消さず吸収）。
  4. **`voice-type` は補助の入口として維持**（集客）。診断後は coach へ送客（実装済み）。
  → IAは「**1つの中心（coach）＋2つの補助（voice-type＝入口／report＝課金面）**」。
- **根拠**: 継続・課金は会話型レッスンの体験に乗る（docs/10）。二重の録音入口は学習導線を
  分散させKPIを薄める。recordings を即削除しないのは、課金の主価値がそこにあり、データ・
  決済との結合を壊さないため（段階移行）。
- **実装への落とし方（チケット分解）**:
  - T-1: グローバルナビ／coach から `recordings/new`（単発アップロード）への新規導線を撤去。
    既存の `recordings` 一覧は「過去の評価アーカイブ」として残す（読み取り専用導線）。
  - T-2: coach の評価結果カードから「詳細添削レポートを見る」を `recordings/[id]/report` へ接続
    （または report をセッション起点で開けるルートを用意）。
  - T-3: 移行期は `recordings` 一覧にバナー「録音は『レッスン』からどうぞ →」を出し coach へ誘導。
- **影響範囲**: 既存ユーザーの過去評価URLは生かす（リンク切れ防止）。課金境界（論点2）と連動。
- **やらないこと（今回）**: recordings の物理削除・DBスキーマ統合は対象外（別フェーズ）。

## 3. 論点2 詳細レポートの課金境界と見せ方

- **決定**: `PREMIUM_REQUIRED` 時は **ティザー表示（見出しだけ薄く見せる）＋アップグレード＋
  「評価に戻る」** を正とする（全閉じにしない・行き止まりにしない）。
- **根拠**: 価値の輪郭を見せた方が転換に効く。行き止まりは離脱を生む（docs/35 課題3）。
- **実装への落とし方**: PR #107 の `report` forbidden 実装が本決定に合致（追認）。
  **docs/31 に「どの画面のどの状態で課金面を出すか」の画面マッピングを追記**
  （評価詳細の「次にできること」／report forbidden／一覧 locked の3点）。
- **影響範囲**: UpgradeModal の `source` は既存3種（limit/report/history）を流用。新規面なし。

## 4. 論点3 生成3分の待ち体験

- **決定（MVP）**: **当面は現状のポーリング（最大3分・5秒間隔）を維持**しつつ、
  **「この画面を離れても生成は進みます」を明示**し、完了は再訪時に表示。
  バックグラウンド＋プッシュ通知は **将来対応（Phase 2）** とし今回はやらない。
- **根拠**: スマホで3分張り付きは非現実的だが、push基盤は未整備。文言明示で離脱の納得感を作る
  のが最小コストの改善。
- **実装への落とし方**: `recordings/[id]/report` の generating 状態に「離れても進む」注記を追加。
  Phase 2 で Web Push もしくはメール通知を別要件化。
- **影響範囲**: フロントのみ（軽微）。バックエンドの生成ロジックは不変。

# 曲名からの原曲解決（検索＋ユーザー確認） 機能要件書

## 1. 概要
- **一言説明**: ユーザーが原曲を「曲名（＋歌手名）」だけで伝えたとき、システムがYouTubeから原曲候補を検索し、「この曲で合っていますか？」と確認したうえで、承諾されたらセッションの原曲参照（`song_ref_url`）として確定する。
- **解決する課題**: 現状、原曲を使った比較（音程の正確さ・リズム）は **YouTube URLの貼り付け or 音源ファイルのアップロード** でしか始まらない。曲名だけ伝えたユーザーには「原曲がないので比べられません」「原曲のファイルを送ってみますか？」を繰り返してしまう。
  - **実害（n=1チャーン分析 2026-07-17）**: 唯一の外部登録ユーザー（7/8）は「原曲　ツキミソウ」と曲名を2回伝え、「これって音程のミスもバシバシ言える？」と本命の要望まで明示したが、応答は毎回「原曲データがないので…アップロードすれば…」。その直後に離脱し、以降再訪なし。**曲名を伝える行為が何の状態変化も起こさない**ことが、コア価値到達を阻んだ。

## 2. 想定ユーザー / ユースケース
- **ペルソナ**: カラオケ・宅録レベルの独学シンガー。「原曲＝曲名を言えば伝わるもの」という感覚。URLを探して貼る手間は初回体験では高いハードル。
- **主要ユースケース**:
  1. 録音FB後に「原曲を教えて」と聞かれ、「ツキミソウ」とだけ返す → 候補提示 → 「はい」→ 次の録音から原曲比較が効く
  2. 最初から「TSUNAMIのサビを見てほしい」と曲名込みで依頼 → 候補確認 → 承諾 → 比較つきFB
  3. 候補が違う → 「違う」と返す → 別候補 or URL/ファイルの案内

## 3. スコープ
### 3.1 対象（やること）
- Web版（`backend/`）の会話返答パスに、曲名→YouTube検索ツール（LLM function calling）を追加
- 確認質問（「この曲で合っていますか？」）を**必須ステップ**とし、勝手に確定しない
- ユーザー承諾の**決定論検出**→ `ChatSession.song_ref_url` / `song_title` への反映
- `docs/42_FB品質基準_単一ソース.md` への作法追記（Web版のみの能力である旨を明記）

### 3.2 対象外（やらないこと）
- Claude Code版 skill への同機能追加（skillはローカル音源の世界。YouTube検索・DL手段が異なるため別案件）
- 検索結果の複数候補UI（チップ・カルーセル等のフロント変更）。テキスト1候補＋確認で始める
- 承諾後の原曲ダウンロード処理の変更（既存 `fetch_reference_wav` のフローをそのまま使う）
- 歌詞・音源の権利処理の変更（既存の「解析目的の一時取得・許可ドメインのみ」の方針を維持）

## 4. ユーザーストーリー
- US-01: ユーザーとして、原曲を曲名だけで伝えたい。なぜならURLを探して貼るのは面倒で、会話なら曲名で通じるのが当然だと感じるから。
- US-02: ユーザーとして、システムが取り違えていないか先に確認してほしい。なぜなら同名曲・カバー・live版で比較先が変わると、その後のアドバイス全部が信用できなくなるから。
- US-03: ユーザーとして、確認に「はい」と答えたら以降は原曲比較が効いてほしい。なぜなら同じ情報を何度も要求されると会話が進んでいない感覚になるから。

## 5. 機能要件

### FR-01: 曲名検出とYouTube検索ツール
- **概要**: 会話返答のLLMに `search_original_song(query)` ツールを追加。ユーザーがURL無しで曲名・歌手名を伝えた（または原曲を尋ねられて曲名で答えた）とき、LLMがこのツールを呼ぶ。
- **詳細仕様**:
  - 実装: `yt-dlp` の `ytsearch3:<query>`（メタデータのみ・ダウンロードなし）。返却は各候補の `title` / `url` / `channel` / `duration_sec`。
  - クエリはユーザーの発言から曲名＋歌手名（分かれば）で構成する。
  - ツールは読み取り専用。セッション状態は**変更しない**（確定はFR-03）。
- **入出力**: 入力=検索クエリ文字列。出力=候補リスト（最大3件）または空。
- **例外ケース**: 検索失敗（ネットワーク・yt-dlp異常）は空リストを返し、LLMは「見つけられなかったので、YouTubeのリンクを貼ってもらえますか？」と正直に案内する（見つかったふりをしない）。

### FR-02: 確認質問（必須・勝手に確定しない）
- **概要**: 検索が成功したら、最有力候補1件を「原曲は『<title>』（<channel>）でしょうか？この曲で合っていますか？→ <url>」の形で提示し、**必ずユーザーの確認を待つ**。
- **詳細仕様**:
  - 応答には固定フレーズ **「この曲で合っていますか？」** と候補URL（1件のみ）を含める（FR-03の決定論検出のアンカー）。
  - 確認を待たずに `song_ref_url` を確定する経路を作らない。
  - ユーザーが「違う」と答えたら、次候補の提示（残があれば）または URL/ファイルアップロードの案内に切り替える。
- **例外ケース**: ユーザーが確認質問に曲名の訂正で返した場合（例「◯◯の方」）は再検索してよい（FR-01に戻る）。

### FR-03: 承諾の決定論検出とセッション反映
- **概要**: 直前のコーチ発言が確認質問（「この曲で合っていますか？」＋許可ドメインURLを1つ含む）で、ユーザーの返答が肯定なら、サーバ側で決定論的に `song_ref_url` を設定する。
- **詳細仕様**:
  - 肯定判定は既存の承諾検出（動画オファー承諾 `_accepts_video_offer` 相当）と同水準の語彙（はい/うん/OK/合ってる/それ/お願いします 等）。
  - 設定内容: `s.song_ref_url = <確認質問中のURL>`。`song_title` 未設定なら既存 `fetch_youtube_title()`（oEmbed）で補完。
  - 反映時の応答は既存のURL受領文言と同じ決定論メッセージ（「原曲を受け取りました😊 次の録音から、照らし合わせてアドバイスしますね🎤」）。LLM生成に依存しない。
  - URLのバリデーション: `is_allowed_url()`（YouTube系ドメインのみ）を必ず通す。**LLMが渡すURLではなく、直前コーチ発言の本文から抽出したURL**を使う（幻覚URL対策）。
- **例外ケース**: 肯定でも直前発言に確認質問が無い/URLが2つ以上ある場合は何もしない（誤発火防止）。

### FR-04: 事実忠実性の維持
- **概要**: 曲名を受け取った時点では比較能力は変わらないことを応答が正しく扱う。
- **詳細仕様**: 確定（FR-03）まで「原曲と比較しました」と言わない。docs/42 §5（原曲なしで正確さを断定しない）は不変。曲名だけ知っている状態を「原曲あり」と扱わない。

## 6. 非機能要件
- **性能**: 検索はタイムアウト20秒。超過時はFR-01例外に落とす（応答不能にしない）。
- **コスト**: ytsearch はメタデータのみ（動画DLなし）。追加API課金なし。
- **保守性**: 確認フレーズ・肯定語彙は定数化し、テストで固定する。

## 7. 受け入れ基準
- AC-01: URL無しで「原曲 ツキミソウ」と送ると、応答に「この曲で合っていますか？」と候補URL1件が含まれる（`song_ref_url` は未設定のまま）。
- AC-02: AC-01の直後に「はい」と送ると、`song_ref_url` が候補URLに設定され、`song_title` が補完され、決定論の受領メッセージが返る。
- AC-03: AC-01の直後に「違う」と送ると、`song_ref_url` は未設定のまま（別候補 or URL案内の応答）。
- AC-04: 検索が0件/失敗のとき、応答は「見つけられなかった」旨＋URL依頼で、候補をでっち上げない。
- AC-05: 確認質問を挟まずに `song_ref_url` が設定される経路が存在しない（ユーザー自身のURL貼付は従来どおり即設定＝対象外）。
- AC-06: 直前コーチ発言が確認質問でないときに「はい」と送っても、`song_ref_url` は変化しない。

## 8. 前提・制約
- 本番backendコンテナから YouTube への到達性がある（既存の原曲DL機能と同一前提）。
- `settings.coach_tools_enabled` がONのときのみツール経路が有効（既存 find_reference_video と同じゲート）。
- 検索結果の品質はYouTube検索に依存する。live版/カバーが最上位に来ることがあるため、確認質問（FR-02）は必須のまま外さない。

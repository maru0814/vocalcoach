# 聴いてから答えるフロー（ブラインド2段階判定＋コメント申告） 機能要件書

## 1. 概要
- **一言説明**: 録音FBを「先入観なしに聴く→聴いた事実の上で講評する」2段階に分け、さらに「何の録音か」をコメント欄の一言で申告できることを明確にする。
- **解決する課題**: 宿題（例: ハミング→母音）と別の練習（例: サイレン）を送った際、レッスン文脈が先入観となり「宿題をやった」前提で録音に無い動作を講評する事故が再発した（docs/52 AC-09 のプロンプト指示だけでは、文脈と録音を同時に渡す構造そのものが残るため不十分な可能性がある）。人間のコーチと同じ「まず聴く、それから考える」をプロンプト指示ではなく**フロー構造で強制**する。

## 2. 想定ユーザー / ユースケース
- **ペルソナ**: レッスン継続中の生徒。宿題以外の練習も自主的に試して録音を送る。
- **UC-01**: 宿題がハミング→母音の状態でサイレンを送る → 「サイレンですね」と聴こえた練習から入る講評が返る。
- **UC-02**: 「サイレンやってみた」と一言添えて録音を送る → 申告を最優先にサイレンとして講評される。
- **UC-03**: 何も添えず歌を送る → 従来どおり歌として講評される（追加操作ゼロ）。

## 3. スコープ
### 3.1 対象（やること）
- ① zero-base FB の前段に**ブラインド聴取**（会話文脈なしの録音単体判定）を追加し、判定結果を講評段に注入する。
- ⑤(A) **コメント欄での申告の明確化**: placeholder で申告を誘導し、コメント内の申告を最優先事実として講評プロンプトに指示する。
### 3.2 対象外（やらないこと）
- 専用タグ選択UI（select）: 実装後に (A)案 へ転換して撤去（FR-03 の背景参照）。
- few-shot 音声例の同梱（打ち手③。①⑤で不足した場合の次弾）。
- 練習識別精度の eval 基盤拡充（打ち手④。別タスクで起票）。
- Claude Code 版 skill（Claude が直接聴くためブラインド段が不要）。
- ルールベースFB経路（zero-base OFF時）の変更。

## 4. ユーザーストーリー
- US-01: 生徒として、送った録音を実際に聴いた上でコメントしてほしい。やっていない練習をやったことにされると信頼が壊れるから。
- US-02: 生徒として、何の練習かをワンタップで伝えたい。毎回説明文を書くのは面倒だから。
- US-03: 生徒として、何も添えなくても今までどおり使いたい。

## 5. 機能要件
### FR-01: ブラインド聴取（第1段）
- **概要**: 講評の前に、録音だけを渡して「何をしている録音か」を判定する専用LLM呼び出しを行う。
- **詳細仕様**:
  - 入力は録音音声のみ。**宿題名・現在課題・会話履歴・ユーザーコメントを一切渡さない**（アンカリング排除の本質）。
  - 練習の既知語彙（リップロール・ハミング・サイレン等、llm.py の既知練習リスト）は「メニュー」として渡してよい（特定の1つを示唆しない）。
  - 出力: `kind`（song|practice）、`practice`（練習名 or 不明）、`confidence`（high|mid|low）、`desc`（聴こえた特徴1文）。
  - モデルは講評と同じ `llm_analysis_model`（聞き分け実績 #288）。出力トークンは小さく制限する。
- **例外**: 呼び出し失敗・パース失敗時はブラインド判定なしとして FR-02 へ（従来の docs/52 フローに自然に退化）。

### FR-02: 講評段への合流（第2段）
- **概要**: ブラインド判定を「聴取事実」として講評プロンプトに注入し、docs/52 FR-04 の第三分岐と組み合わせる。
- **詳細仕様**:
  - intent_ctx に `blind`（FR-01の結果）を追加し、プロンプトへ「ブラインド聴取の判定: サイレン（確信度high）— <desc>」の形で注入する。
  - 判定の優先順位: **ユーザー申告（FR-03）＞ ブラインド聴取 ＞ 音響ヒューリスティック（resolve_kind）＞ 会話文脈**。
  - INTENT タグの出力・書き戻し・ルーティング（docs/52 FR-04）は現行踏襲。ブラインド判定が practice の場合も、最終 INTENT は講評モデルが宣言する（ブラインドは事実の注入であり強制ではない）。
- **例外**: ブラインド判定が無い場合は現行 docs/52 フローのまま。

### FR-03: コメント欄での申告（(A)案・2026-08-08 改訂）
- **概要**: 「この録音は何か」の申告は、専用タグUIではなく**既存コメント欄の自然言語**で行う（例:「サイレンやってみた」）。
- **背景（改訂理由）**: 当初はタグ選択UI（select）を実装したが、(1) 過去に「送信種類トグル廃止」で消したUIの復活になる、(2) 会話レイヤー刷新（意図理解をLLMに返す・ルールベース排除）の思想と逆行する、(3) 申告するには毎送信タップが要る、の3点からUIを撤去し会話チャネルに一本化した（プロトタイプ比較の上でユーザー決定）。
- **詳細仕様**:
  - コメント欄の placeholder に申告誘導を含める（例:「質問や『サイレンやってみた』のような一言を添えて録音・アップロードすると、そこから聴きます」）。
  - `user_comment` がある場合、講評プロンプトに「コメントで何の録音かを伝えている場合は最優先の事実として講評する（録音が申告と明らかに食い違う時だけ、決めつけずに正直に一言確認する）」の指示を含める。
  - 新しいAPIフィールドは追加しない（既存 `comment` のみ。後方互換は自明）。
- **例外**: コメント無しは従来どおり（ブラインド聴取＋第三分岐が効く）。

### FR-04: コスト計上
- **概要**: ブラインド呼び出しの原価を llm_budget に計上する。
- **詳細仕様**: ブラインド1回の概算単価を設定に追加し（出力が小さいため講評より安い概算でよい）、zero-base 実行時に講評分と合わせて record する。無料ユーザーの月次上限（¥2,000, docs/52）の判定対象に含める。

### FR-05: ブラインド失敗時の正直な保留（2026-08-13 追加）
- **概要**: ブラインド聴取が失敗した場合、講評段を**当て推量で進めない**。正直に「聴き取れなかった」と伝えて再送を促す。
- **背景（実事故）**: 2026-08-13、サイレン録音に対しブラインド段が無言で失敗（`except: return None`・ログ皆無）し、講評段が文脈頼みで「歌」と誤認・作話した。同じ録音での再現実験ではブラインド段は2回とも正答（サイレン・確信度high）＝能力ではなく**失敗の握りつぶし**が原因。
- **詳細仕様**:
  - ブラインド1試行の失敗（API例外・パース不能）は必ず WARNING ログに残し、**1回だけリトライ**する。成功時も判定内容を INFO ログに残す（効いた回/効かなかった回を後から区別可能に）。
  - 2回とも失敗した場合、講評（generate_feedback）・ルールベースFBのいずれにも進まず、「いま録音をうまく聴き取れませんでした。少しおいてもう一度送ってください」と正直に返して終了する。
  - このとき無料ユーザーの解析回数は**消費しない**（カウントは正常系の最後で行う）。
  - `ENABLE_BLIND_LISTEN=false` の環境ではこのゲート自体が無効（従来どおり）。
- **例外**: 予算上限でブラインドを計画しなかった場合（ルールベースFBへの意図的な格下げ）はこの限りではない。

### FR-06: 種類の確定と歌アンカーの除去（2026-08-13 追加）
- **概要**: ブラインド聴取が**確信度highで「発声練習」**と判定したら、講評段は歌として講評できない（種類はコードで確定）。歌前提の材料（原曲音声・原曲比較データ）は講評段に**そもそも渡さない**。
- **背景（実事故・FR-05適用後）**: 原曲（ライラック）登録済みセッションでサイレンを送信。ブラインド段は「practice・確信度high」を返しログにも残ったが、講評段のプロンプトには原曲音声＋比較データが同梱されており、「練習です」のメモ1行が文脈の物量に負けて歌講評（原曲比較つき）が生成された。プロンプト指示の優先付けでは不十分＝**アンカー自体を排除し、種類はコードで固定**する必要がある。
- **詳細仕様**:
  - `blind.kind == "practice" かつ confidence == "high"` のとき:
    - `intent_ctx["forced_intent"] = "practice"` を設定。講評プロンプトは歌/練習の二択を出さず「発声練習（確定）」として指示。INTENT タグの書き戻しもコードで practice に固定（モデルが song を返してもログを残して無視）。
    - ref_wav（原曲音声）・`_compare`（原曲比較データ）を講評段に渡さない。
    - ルーティング（kind）も practice に確定。
  - **練習名は確定しない**: ブラインドの練習名は推定（サイレンをリップロールと聴き間違えた実例あり）。講評は名前に確信が持てなければ断定せず、聴こえた動きの描写（「低い音から高い音へなめらかにつなぐ練習」）か一言確認で語る。
  - 確信度 mid/low の practice 判定・song 判定は従来どおり（注入事実として渡すのみ。song を強制しないのは「歌を練習と誤確定」する逆事故を防ぐため＝非対称設計）。
- **例外**: `ENABLE_BLIND_LISTEN=false` では無効（従来どおり）。

## 6. 非機能要件
- **性能**: ブラインド段の追加でFB応答が体感悪化しないこと（タイムアウトは講評と別に短め＝30秒以内。リトライ込み最悪60秒＋講評）。
- **コスト**: 1インタラクションあたり概算 ¥0.9 以下（講評¥0.44＋ブラインド）。docs/52 の粗利前提を壊さない。
- **保守性**: `ENABLE_BLIND_LISTEN` で①を単独ON/OFFできる。⑤(A) はコメント未記入なら挙動不変。

## 7. 受け入れ基準
- AC-01: ブラインド聴取のプロンプトに、宿題名・現在課題ラベル・会話履歴・ユーザーコメントのいずれも含まれない（自動テストで検証）。
- AC-02: ブラインド判定が得られた場合、講評プロンプトに「ブラインド聴取の判定」が注入される。
- AC-03: コメント付きで録音を送ると、講評プロンプトに「コメント内の申告を最優先の事実として講評する」指示が含まれる。
- AC-04:（FR-05 で改訂）ブラインド呼び出しが2回とも失敗した場合、当て推量の講評ではなく「聴き取れなかった・再送してほしい」の正直な返答が返る。
- AC-05: ブラインド実行時、llm_budget に講評＋ブラインドの合計原価が記録される。
- AC-06: APIリクエスト形式は現行と同一（新規フィールドなし・後方互換は自明）。
- AC-07: docs/52 AC-09 の既存回帰テストがパスし続ける（第三分岐は維持）。
- AC-08: `ENABLE_BLIND_LISTEN` OFF で①が完全に無効化され、⑤(A)（コメント申告の指示）は独立して動く。
- AC-09: ブラインド1試行目が失敗し2試行目が成功した場合、講評は通常どおり生成される（リトライが効く）。
- AC-10: ブラインドの成功（判定内容）・失敗（理由）が必ずログに残る（無言の失敗が存在しない）。
- AC-11: FR-05 の再送依頼パスでは、無料ユーザーの月次解析回数を消費しない。
- AC-12: `forced_intent=practice` のとき、講評プロンプトに歌/練習の二択が現れず「発声練習（確定）」として指示され、練習名を断定しない注意が含まれる。
- AC-13: `forced_intent=practice` のとき、モデルが `INTENT: song` を返しても `heard` は practice に固定される（警告ログつき）。
- AC-14: blind が practice/high のとき、講評段に ref_wav・原曲比較データ（`_compare`）が渡らない。

## 8. 前提・制約
- zero-base FB 有効環境（docs/52）が前提。モデルは gemini-3.5-flash（#288 の聞き分け実績）。
- FB品質・事実忠実性の正本は docs/42（変更なし。本要件は42の「録音に無いことを言わない」を実現する手段）。

## 0. なぜ統合するか（パッチワークの清算）
docs/95 の FR-04〜07 は、実事故のたびに講評プロンプトへ足した絆創膏の積層である：
- FR-04/AC-09: 「決めつけるな」の指示文（→ 3度破られた）
- FR-06: 「練習」確定の強制＋原曲アンカー除去
- FR-07: 宿題名の講評禁止ガード

事故は毎回、**同じ一つの根本原因**の別の顔だった：
> 講評段（第2段）が「これは何の録音か」を再判定できてしまう。第2段には文脈の山（宿題・課題・原曲・比較・カルテ）が渡るため、再判定は毎回どれかのアンカーに負ける。

本設計はこれを**職務分離**で根治する。識別は識別レイヤーの専権とし、講評段からは「何の録音か」を判断する権利そのものを取り上げる。特例プロンプト群は単一の識別コントラクトに畳んで削除する。

## 1. 原則
1. **識別は一度だけ・一箇所で**。識別レイヤー（ブラインド聴取＋質感DSP＋ユーザー申告）だけが録音の正体を決める。
2. **講評段は識別を再判定しない**。識別結果は所与の事実。講評段の仕事は「その録音として、どうだったか」だけ。
3. **迷ったら当てずに聞く**。識別が名前に確信を持てない時は、描写で語り一言確認する（人間のコーチと同じ）。会話で解決するのは docs/93/94 の路線そのもの。
4. **文脈は識別結果でフィルタして渡す**。練習と識別されたら、歌前提の材料（原曲音声・比較データ）は講評段の入力に最初から存在しない。
5. **精度投資は識別レイヤー一点に集中**。DSP（docs/104）・eval・few-shot はすべてここへ。講評プロンプトに聞き分けの知恵を足さない。

## 2. 識別コントラクト（Identity）
識別レイヤーの出力は次の1オブジェクトに統一する：
```python
identity = {
    "kind": "song" | "practice",       # ルーティングと講評様式を決める（必須）
    "name": str | None,                 # 練習名（確信がある時だけ。歌は None）
    "confidence": "high" | "mid" | "low",
    "description": str | None,          # 聴こえた事実の描写（例: 低→高へなめらかに移動）
    "source": "declared" | "blind" | "heuristic",  # 出所（申告・聴取・音響推定）
}
```
### 決定手順（coach.py・優先順位は docs/95 と同じ）
1. **ユーザー申告**（コメント内の宣言。将来UI申告が復活してもここ）→ `source="declared"`, confidence=high
2. **ブラインド聴取**（`listen_blind`＋質感DSP注入）→ そのまま採用。2回失敗時は識別不能＝FR-05 の正直保留（変更なし）
3. **フラグOFF時**（`ENABLE_BLIND_LISTEN=false`）→ `resolve_kind` の音響ヒューリスティック → `source="heuristic"`, confidence=low, name=None

### ルーティング
`kind` は identity.kind をコードで採用（講評段の出力からは決めない）。**INTENT タグ プロトコルは廃止**（docs/52 FR-04 の「モデルがタグを宣言→書き戻し」は、識別の専権化により不要。タグ骨抜き・書き戻し固定などの補助ガードも全て削除）。

## 3. 講評プロンプト（第2段）の再構成
特例ブロック（forced_intent 分岐・宿題名ガード・(a)/(b)二択・INTENT指示）を全廃し、常に単一の識別ブロックを注入する：
```
# この録音について（識別済み・ここは再判定しない）
種類: 発声練習（確信度 high）
聴こえた内容: サイレン — 低い音から高い音まで連続的に約24半音移動
（または: 名前は特定できていない — 「低→高へなめらかにつなぐ練習」のように描写で語り、最後に一言確認する）
ルール:
- この識別と異なる名前（勧奨中の基礎練名・原曲名を含む）でこの録音を講評しない
- 種類が「発声練習」の時、歌としての講評（音程の正確さ・原曲比較・ビブラート評価）はしない
- 名前が未特定の時、講評は描写ベースで行い、断定しない
```
- 名前確定（confidence=high かつ name あり）→ 名前で講評
- 名前未確定 → 描写で講評＋「〜の練習で合っていますか？」を応答末尾の1問に使ってよい（docs/42 の1問ルール内）
- 種類 song → 従来の歌講評（原曲・比較材料あり）

### 入力フィルタ（coach.py）
- identity.kind == "practice" → `ref_wav` と `last_analysis["_compare"]` を渡さない（FR-06 の一般化）
- identity.kind == "song" → 従来どおり

## 6. テスト方針
- 既存の INTENT 系テスト（test_zero_base_gate.IntentAwareListening ほか）は新コントラクトのテストに置換：
  - identity 決定手順（申告>聴取>ヒューリスティック／フラグOFF時 heuristic）
  - プロンプト: 識別ブロックの内容（名前確定/未確定/歌の3態）・特例文の不在（forced_intent 文言・宿題名ガード文言・INTENT 指示が消えている）
  - kind ルーティングが identity.kind に従う
  - 練習識別時に ref/_compare が渡らない
- 回帰: docs/52 の原事故（宿題と別練習）・8/13〜14 の実事故（歌誤認・宿題名誤認）をシナリオテスト化。

## 7. リスクと緩和
- **識別が間違うと講評ごと間違う**（再判定の余地を消すため）→ 緩和: 名前は確信時のみ断定・未確定は描写＋確認、eval で識別精度を計測して投資判断（docs/104）。ユーザーの一言（「これサイレンだよ」）への訂正対応は会話レイヤー（docs/93）が既に担う。
- **歌の誤識別**（practice と誤確定）→ ブラインドが song を返せばそのまま歌講評であり、従来より悪化しない。eval で監視。

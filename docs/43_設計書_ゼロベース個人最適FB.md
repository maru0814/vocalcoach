# ゼロベース個人最適FB 設計書

## 0. 背景・目的
現状の録音FBは **「測って → 固定カタログから課題を1つ選んで → 言い換える」** 構造で、個人最適が「約10個のバケツのどれか」に頭打ちになっている。これを **「音声をゼロベースで聴いて、証拠から推論し、完全にパーソナライズしたFBを生成する」** 方式へ根本転換する。

- 関連: docs/42（FB品質SSOT）, docs/12（反ハルシネーション）, docs/22（発声特化）
- 意思決定（丸山CEO 2026-06-29）: **ハイブリッド（DSP＋生音声）** / **分析ターンだけ強モデル** / **Phase 1〜2を実装**

## 1. 現状の「選択肢から選ぶ」構造（問題の所在）
```
audio → analyzer.py        … 音響特徴を実測（f0/jitter/H1-H2/CPP/フォルマント/DTW）★本物
      → rule_engine.handle_audio … taxonomy.TASKS を閾値diagnose()で1つ選定（録音FBの本線）
      → taxonomy.py         … 固定 reason文 + 固定 practices(steps/動画URL)
      → voice_coach.py      … issue判定→該当 EXERCISES(A1〜F2固定DB)だけ注入
      → llm.py(generate_reply) … 雑談のみ。「候補に無いエクササイズを創作しない」と蓋
```
- 録音FB本線: `backend/app/api/v1/endpoints/coach.py` の `POST /sessions/{id}/audio` → `rule_engine.handle_audio`
- カタログ: `taxonomy.TASKS`（約10課題）/ `voice_coach.EXERCISES`（A1〜F2）

## 2. 設計原則：2つの仕事を分離する
| 仕事 | 旧 | 新 |
| --- | --- | --- |
| **接地（ハルシネーション防止）** | メニュー制限（候補外禁止） | **引用規律**: 全測定主張が Evidence Pack の実測値に紐づく |
| **診断＋処方（個人最適）** | 閾値ルール＋固定カタログ | **証拠からモデルが推論して生成** |

> **境界線**: モデルは「アドバイスの組み立てと言葉」は自由（個人最適）。「測定値（秒・音名・cents・息漏れ等）の捏造」は禁止。**解釈は自由、証拠は不可侵。**

## 3. 新アーキテクチャ：Evidence → Reason → Ground → Speak
1. **Evidence Pack（生の証拠一式）**: 事前選定した1課題ではなく、区間ごとのタイムライン（秒/音名/声区推定/centroid/jitter/H1-H2）・DTWズレ箇所・原曲比較差分・全体特徴を構造化して渡す。全て実測＝真実。
2. **Pedagogy KB（参照知識）**: `EXERCISES`(A1〜F2)・解剖学原則を「IDを選ぶ」から「モデルが参照して*この人向けに調整・連結*する知識」へ再配置。機構を引用しつつキューをパーソナライズ。
3. **Reason step**: 「この証拠から、この歌い手に今いちばん効く1点は？なぜ？どの機構で？最も刺さる練習とキューは？」を推論。優先順位（声基礎欠損>音程>ミックス>リズム>表現）は**ゲートでなく指針**。→ **推論モデル必須**。
4. **Ground & Speak**: 全事実主張を Evidence Pack に追跡可能に。`_scrub_invented_seconds` を維持＋未接地の数値/位置を抑制。

## 4. ハイブリッド音声（「ゼロベースで聴く」）
- **DSP特徴（analyzer）**: cents/秒の正確な接地。**残す**＝嘘を防ぐ土台。
- **生音声→マルチモーダル**: 音色・感情・発音・歌い回し・「原曲らしさ」等 DSPが測れない全体質。
- **両方をモデルに渡す**。既存の音声基盤（`llm.analyze_pronunciation` / `classify_register_audio` が `llm_audio_model` で `Part.from_bytes(audio/wav)`）を一般化して流用する。

## 5. モデル・ルーティング（コスト規律 docs/29 と両立）
| ターン | モデル | thinking | 理由 |
| --- | --- | --- | --- |
| 録音FB（分析ターン） | `llm_analysis_model`（強・例: gemini-2.5-pro） | 有効 | 証拠から推論・音色判断。回数が少ないので費用影響小 |
| 雑談ターン | `llm_model`（Flash-Lite） | 無効 | 短い受け答え。安く速く |
- 強モデルは**録音を受けた初回FBのターンだけ**。月¥2000方針は維持（分析ターンは1録音1回）。

## 6. 実装（Phase 1〜2・additive・フラグでgate）
**安全方針**: 新経路は `enable_zero_base_fb`（既定OFF）でgate。ONにするまで本番挙動は不変。失敗時は既存のルールベースFBへフォールバック（会話を止めない）。

### 6.1 `core/config.py`
- `enable_zero_base_fb: bool = False`（既定OFF）
- `llm_analysis_model: str = "gemini-2.5-pro"`
- `llm_analysis_max_tokens: int = 1200`
- `llm_analysis_thinking_budget: int = 2048`（>0で推論有効）
- `llm_analysis_timeout_sec: float = 90.0`

### 6.2 `coaching/llm.py`
- `build_evidence_pack(state) -> str`: 全タイムライン区間・原曲比較差分・全体特徴を構造化（事前選定の1課題を含めない）。
- `render_exercise_kb() -> str`: `voice_coach.EXERCISES` を「参照知識」として整形。
- `ANALYSIS_SYSTEM_PROMPT`: メニュー制限を撤廃し、引用規律＋KB参照＋Reason step＋優先順位指針を明記。
- `generate_feedback(state, user_wav=None, ref_wav=None) -> Optional[str]`: 分析ターン。強モデル＋thinking＋ハイブリッド音声＋Evidence Pack。`_scrub_invented_seconds`/`scrub_card_promise` 適用。失敗時 None。

### 6.3 `api/v1/endpoints/coach.py`（録音ハンドラ）
- `enable_zero_base_fb` がONなら、`rule_engine.handle_audio` の前に `llm.generate_feedback(state, user_wav, ref_wav)` を試み、成功すればその講評を録音FBメッセージにする。Noneなら従来のルールベースFBにフォールバック。

## 7. 接地（ハルシネーション防止）の担保
- Evidence Pack の数値・秒のみ言及可。`_allowed_seconds` は Evidence Pack 文字列から構築されるため、注入した秒は許可される（捏造分は `_scrub_invented_seconds` で抑制）。
- 原曲照合が low_confidence の時はリズム・音程の正確さを断定させない（既存ルール踏襲）。
- カタログ外の練習は**作ってよい**が、機構（なぜ効くか）を必ず述べさせる＝でたらめ抑止。

## 8. 検証・ロールアウト
1. `enable_zero_base_fb=1` で staging 検証（既存 `backend/tests/test_conversational_fb.py` ＋ 実録音でA/B）。
2. 接地チェック（返答中の秒/数値が Evidence Pack に存在するか）。
3. コスト計測（分析ターンの単価×録音数）。問題なければ本番でフラグON。

## 9. 将来（本設計の外）
- Reason step の中間出力（診断JSON）を保存し、Phase E の改善判定に再利用。
- 自動診断ルール（taxonomy）は「保険」として残し、強モデル不調時のフォールバック品質を担保。
